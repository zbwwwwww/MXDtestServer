# 「双击角色进不去」最终根因报告

> 排查时间：2026-09-20 21:40 ~ 22:05
> 结论性质：**已用 jstack 线程快照 + 实测复现钉死，非推断**

---

## 一句话结论

**服务端被一条卡死的 MySQL 连接锁住了整个地图加载系统。**
`main` 线程在建立数据库 TCP 连接时永久阻塞（`SYN_SENT`），而它**持有着 `MapleMapManager` 的锁**；
你的登录线程和 4 个定时器线程全部在**等这把锁**。
所以：客户端连上了频道服 7575，但服务端永远走不到"发角色数据"那一步 →
**双击没反应、服务端一声不吭、数据库状态停在 `loggedin=1`**。

**这不是你的操作造成的，也不是代码逻辑错误。是机器端口池被打满导致的系统级故障。**

## 二、为什么会有条连接卡住

```
TCP  127.0.0.1:51117  →  127.0.0.1:3306  SYN_SENT   PID 30816
```

`SYN_SENT` = **握手包发出去了，对面不回**，卡了 20 分钟以上。

原因：**本机动态端口池被打满**。

| 指标 | 数值 |
|---|---|
| 动态端口范围 | `49152 ~ 65535`，共 **16384** 个 |
| 当前 `TIME_WAIT` 总数 | **18,648 个**（超了 2,264 个） |
| 其中去 **443** 端口的 | **11,748 个** |
| 去 80 端口的 | 1,924 个 |
| 去 8081 端口的 | 1,416 个 |
| 去 3306（MySQL）的 | 791 + 1,309 个 |

端口池满 → Windows 进入 **SYN 洪水保护**，丢弃新的握手包 → `connect()` 挂着等。
而 MySQL 驱动 `connectTimeout` **默认是 0 = 永不超时**（`config.yaml` 的 DB_URL 没设这个参数），
所以这条连接不是"慢"，是**永远不返回**。

### 谁把端口池占满的（实测归属）

| 进程 | 说明 |
|---|---|
| **WorkBuddy.exe**（3 个进程） | 采样到持续在开 443 短连接 —— 主力贡献者 |
| MsMpEng.exe | Windows Defender 实时保护 |
| 另外还有本机另一张网卡 `192.168.0.113`（8,837 个） | 与本机 `192.168.0.115` 并存 |

**服务端自己也在贡献**：`java.exe` 到 3306 有 1,309 个 `TIME_WAIT`，约 **5 条连接/秒** ——
因为 `new DatabaseConnection()` 在**全项目零调用**，`DB_CONNECTION_POOL: true` 从来没生效过，
所以**每一条 SQL 都新建一条 TCP 连接**。

## 四、怎么修

### 立刻能进游戏（唯一快速路径）

> **重启 Windows** → 端口表清零 & SYN 保护重置 → 尽快启动服务端 → 登录

顺序很重要：

1. 关掉游戏客户端
2. **重启 Windows**（立刻清空 18,648 个 TIME_WAIT）
3. 重启后**尽快**启动服务端（在端口表被重新填满之前）
4. 等控制台出现 `Listening on port 8484` + `HeavenMS is now online`
5. 登录 → 双击 `ceshi`

> 为什么必须重启：眼下这把锁是**永久锁死**的（JDBC 无超时），
> 不重启的话，只关掉服务端再开，端口池依然是满的，启动时**大概率再次卡死**。

### 治本（防止复发，两项都建议做）

| # | 改什么 | 效果 | 代价 |
|---|---|---|---|
| **G**（安全网，强烈建议） | `config.yaml` 第 165 行：<br>`DB_URL: "jdbc:mysql://127.0.0.1:3306/heavenms?connectTimeout=5000&socketTimeout=15000&autoReconnect=true"` | 卡死 → **5 秒超时**。以后再遇到端口紧张，只是"某次操作失败"，**不会再把整个服务端锁死** | 只改配置，**不用重编译**，重启生效 |
| **E**（根因） | 在 `Server` 启动流程里调用一次 `new DatabaseConnection()`（该类全项目零调用，所以连接池一直是摆设） | 服务端到 MySQL 的 TCP 连接从 **~5 条/秒** 降到 10~30 条常驻，端口池压力降 99% | 改 Java，要重编译 |

### 可选（系统级，需管理员）

- 扩大动态端口范围，立刻生效、不用重启：
  ```cmd
  netsh int ipv4 set dynamicport tcp start=10000 num=55535
  ```
- 或降低 TIME_WAIT 保留时间（注册表 `TcpTimedWaitDelay`），**需要你同意**再动。

### 顺手做（不用改代码）

- 减少后台常驻的联网软件（WorkBuddy/CEF、Defender 的实时扫描）在长时间游戏时的干扰
- 建议服务端**不要**和大量开 HTTPS 短连接的程序长期同时运行

## 六、这次故障的完整因果链

```
后台程序狂开 HTTPS 短连接（WorkBuddy/Defender 等）
        ↓
+ 服务端每条 SQL 新建一条 TCP 连接（连接池从未启用）
        ↓
TIME_WAIT 累积到 18,648 个 > 动态端口上限 16,384
        ↓
Windows 启用 SYN 洪水保护，开始丢弃新握手包
        ↓
服务端启动时读 plife（刷怪点）建连 → SYN 发出去没人回 → 永久阻塞
        ↓
该线程持有 MapleMapManager 锁不放
        ↓
你双击角色 → 登录线程要加载地图 → 等锁 → 永久 BLOCKED
        ↓
客户端反复重连 7575 又被挂住 → 「双击没反应」「服务端零日志」
```

## 七、第三轮补充（2026-09-20 21:56）—— 卡点精确定位到「启动阶段」

### 完整调用栈（比第一轮更精确）

第一轮只看到 `main` 卡在 MySQL 建连；这一轮抓到了**完整的 22 层栈**，卡住的位置在**服务端启动流程**里：

```
net.server.Server.main(Server.java:885)
 → Server.init(Server.java:852)
 → Channel.reloadEventScriptManager(Channel.java:191)   ← synchronized，持 Channel 锁
 → EventScriptManager.<init>(:66) → EventScriptManager.init(:86)
 → Nashorn 事件脚本 Script$Recompilation$659$379$^eval_ .init(<eval>:25)   ★ 脚本第 25 行调了 getMap()
 → MapleMapManager.getMap(MapleMapManager.java:92)       ← synchronized，持 MapleMapManager 锁
 → MapleMapManager.loadMapFromWz(:68)
 → MapleMapFactory.loadMapFromWz(:243)
 → MapleMapFactory.loadLifeFromDb(:86)                   ← 读 plife 表
 → DatabaseConnection.getConnection(:33)
 → DriverManager.getConnection → com.mysql.jdbc ... connect0   ← 永久阻塞
```

**这意味着：服务端其实「没启动完成」。**

- 8484 / 7575 显示 `LISTENING`，是因为 MINA 的 acceptor 在 `Channel.init()` 里**先绑端口、后加载事件脚本**；
- 但 `Server.init()` 卡在脚本加载那一步，永远走不到最后；
- 所以**整个登录流程从未就绪** —— 你双击角色，服务端根本没有能力处理。

> ✅ **判断服务端是否真的起来了**：看 IDEA 控制台有没有出现 `Channel 1: Listening on port 7575`。
> 只看「端口在监听」是不够的。

### 第三轮实测数据

| 项 | 值 | 判读 |
|---|---|---|
| `TIME_WAIT` | **18833** | 仍超上限 16384 |
| 远端端口分布 | 443→11886 / 80→1934 / 8081→1418 / 3306→793 | 制造者是 `WorkBuddy.exe` 与 `MsMpEng.exe` |
| MySQL 直连测试 | ✅ 5/5 全通 | 端口压力是**波动**的，但服务端那条老连接已经死透 |

| `config.yaml` 修改时间 | **21:54:57** | 用户已自行给 `DB_URL` 加上 `connectTimeout=5000` |

### 关键：配置改了，但进程是旧的

`config.yaml` 的 `DB_URL` 已经改好（加了超时参数），但**当前这个服务端进程是在改配置之前启动的**，跑的仍是「无超时」的旧设置 —— 卡死照旧。

**TCP 超时参数只在建立新连接时读取。改完配置必须重启服务端。**

### 清空 TIME_WAIT 的两条路（二选一）

| 方案 | 操作 | 要重启电脑吗 | 生效速度 |
|---|---|---|---|
| **A** | **以管理员身份**打开 CMD，执行：<br>`netsh int ipv4 set dynamicport tcp start=10000 num=55535`<br>（端口数 16384 → 55536） | ❌ 不用 | 立即 |
| **B** | 开始菜单 → 电源 → **重启** | ✅ 要 | 重启后 |

> 方案 A 可随时改回：`netsh int ipv4 set dynamicport tcp start=49152 num=16384`

### 正确的操作顺序

1. IDEA 里 **Stop** 掉卡死的服务端
2. 执行方案 **A** 或 **B**（清空端口池）
3. IDEA 里 **Run** 重启服务端
4. 等控制台出现 `Channel 1: Listening on port 7575` **且** `HeavenMS is now online`
5. 双击 `单机登录器.bat` → 登录 → 双击 `ceshi`

> 第 3 步之后如果还卡，`connectTimeout=5000` 会让它 **5 秒内报错**而不是永久挂住 —— 那样我们就能在 IDEA 控制台看到真正的异常，不用再猜。
