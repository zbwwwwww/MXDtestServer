## 2. 最重要的认知修正：「吸怪」其实是两件完全不同的事

这是本次调研最值钱的一条，直接决定实现方案：

| 方式 | 服务端做什么 | 客户端会照做吗 | 现状 |
|---|---|---|---|
| **移动已有怪**<br>`mob.resetMobPosition(pos)` | 发 `moveMonster` 包改位置 | ⚠️ **不一定** —— 怪的位置本来由客户端驱动（`MoveLifeHandler`），服务端只是转发 | 已接 F2 键，**至今未实测通过** |
| **召唤新怪到脚下**<br>`map.spawnMonsterOnGroundBelow(id,x,y)` | 发 `spawnMonster` 包 | ✅ **一定** —— 怪"出生"就在那，客户端没有反驳余地 | 菜单 `#L19#` 已在用，**已验证** |

⇒ **想让"隔壁图的怪出现在我脚下"，用「复制+在脚下召唤」比「搬位置」可靠得多。**
`resetMobPosition` 那条路（全项目零调用方）能不能生效，还是个悬案。

|---|---|---|---|

1. 遍历 `getPortals()`，筛 `getType() == 2`（`MaplePortal.MAP_PORTAL`）
2. `getTargetMapId()` 去重、排除 `999999999`

所以 1a/1b 要准备好"该图暂时没有怪"的提示，或者走**读 wz `life` 节点**的兜底（复杂一档）。

## 10. 原理：吸过来的怪为什么会乱跑？外挂"定怪"是怎么做到的？

> 用户晚上的疑问：F2 吸怪后，怪会散开、左右跑、到处跑；而别人外挂吸怪时，怪只在很小范围动甚至完全不动。差异在哪？

### 10.1 先看清 F2 吸怪到底干了什么

`gm_menu.js:1442` 调 `mob.resetMobPosition(pos)`，服务端实现是 `MapleMonster.java:1325`：

```java
public void resetMobPosition(Point newPoint) {
    aggroRemoveController();                              // ① 解除当前控制器
    setPosition(newPoint);                                // ② 服务端把怪瞬移到脚下
    map.broadcastMessage(moveMonster(... getIdleMovement() ...)); // ③ 广播"怪移动了"（idle 动画，不立即走动）
    map.moveMonster(this, this.getPosition());            // ④ 更新服务端坐标 + 可见性
    aggroUpdateController();                              // ⑤ 重新分配控制器（立刻又对你 aggro）
}
```

**关键点**：`resetMobPosition` 只是"瞬移 + 重新挂上 AI"。它**没有、也不可能让怪停下来**——
因为第 ⑤ 步 `aggroUpdateController()` 让怪重新认你做主人，怪的 AI 立刻开始**追你**。

### 10.2 怪的"走动"到底谁在驱动？（这是核心）

**服务端自己不模拟怪物行走**。`MapleMonster` 里的 `TimerManager` 只用于技能冷却 / 掉落 / 木偶仇恨（`MapleMonster.java:772/831/2181`），
**没有任何"怪物巡逻/追击"的定时线程**。怪的位移来自：

1. 某玩家 aggro 了这只怪 → 该玩家的客户端成为"控制器"（`MapleCharacter.controlMonster`，`:1970`）。
2. 客户端本地的怪物 AI 算出"该往哪走"，发出 `MOVE_LIFE` 包（`RecvOpcode.MOVE_LIFE` → `MoveLifeHandler`）。
3. `MoveLifeHandler.java:163/173`：`updatePosition(slea, monster, -2)` 把**客户端报上来的位移**直接套到怪的服务端坐标，
   再 `map.broadcastMessage(moveMonster(...))` **转发给其他人**。

⇒ **服务端对怪物移动是"盲信客户端 + 纯转发"**。客户端说往哪走、走多远，服务端就信、就广播。

### 10.3 所以"乱跑"和"定怪"是同一件事的两面

| 现象 | 谁在动怪 | 服务端看到什么 |
|---|---|---|
| F2 吸怪后到处跑 | 你的客户端对脚下这些怪 aggro 了，本地 AI 让它们**追你** → 不断发 `MOVE_LIFE` | 收到位移包 → 应用 + 转发 → 怪就游走、散开 |
| 外挂"定怪" | 外挂**劫持了**它作为控制器的那只怪的移动生成：把"追你"的位移**替换成"原地不动 / 极小抖动"** | 收到的全是"几乎不动"的包 → 应用 + 转发 → **所有人看到怪钉死** |

**结论**：外挂的"定怪"不是服务端功能，是**纯客户端/网络层技巧** —— 它控制了怪的 `MOVE_LIFE` 包内容，
把正常的追击位移改成"零位移"或"小幅抖动"。因为服务端盲信控制器客户端，所以全服都看到怪不动。
这就是你看到的"很小范围移动（小幅抖动）"和"完全不动（零位移）"两种表现的来源。

### 10.4 那我们服务端这边能不能" legit 地定怪"？

能做，但需要**改 Java + 重编译**（不走纯脚本路线），三种思路：

| 思路 | 做法 | 改动量 | 评价 |
|---|---|---|---|
| **A. 冻结标志位** | 在 `MapleMonster` 加 `frozen` 字段；`MoveLifeHandler.java:163` 处若 `monster.isFrozen()` 则跳过 `updatePosition`（只更新朝向），并把 `aggroUpdateController` 改成不追玩家 | 中（改 2 个文件 + 吸怪脚本里置位） | **最干净**，吸完即钉死，且不打客户端包 |
| **B. 关闭移动动画** | 召唤时把该怪 `MapleMonsterStats` 的 `animationTimes` 去掉 `move`/`fly` → `isMobile()` 返回 false（`MapleMonsterStats.java:140`） | 中（重载 stats） | 怪彻底不走动画，但会"飘"在原地，且是 per-类型 |
| **C. 定时回拉** | 吸怪后起一个定时器（如每 200ms）反复 `resetMobPosition` 钉在脚下 | 小（脚本 + 一个 Timer） | 会和客户端 `MOVE_LIFE` 打架、画面闪烁，**不推荐** |

> 思路 A 最适合配合"召唤点名"做成"吸过来 + 钉死"一条龙。但属于**新功能**（用户尚未要求），
> 等你想做再单独立项、走"先给 diff 再动手"流程。
> ⚠️ **A 与 C 互斥、不叠加**：A = 源头不让坐标变（`MoveLifeHandler` 跳过 `updatePosition`，根本不发移动包）；C = 坐标被客户端改了、每 200ms 拉回。A 生效时坐标本不变，C 拉的是空操作；C 生效时 A 多余。两者同开只浪费资源、行为还可能打架。**二选一，推荐 A**。

### 10.5 一句话总结

- **乱跑**：F2 只瞬移、不锁 AI，怪被你的客户端驱动着追你 → 自然散开游走。
- **定怪**：外挂在它作为控制器的一端，把怪的位移包改成"零/极小"，服务端盲信 → 全服看到不动。
- **想在服务端 legit 复现**：思路 A（冻结标志 + MoveLifeHandler 跳过位移）最稳，但要改 Java。

### 10.6 外挂的「连续自动吸怪」是怎么实现的（2026-09-22 追加）

**现象**：怪被打死后，原位置刷新新怪，外挂又自动把新怪吸过来——像有循环在一直吸。

**先排除两个错误假设（均有服务端代码铁证）**：

| 假设 | 是否成立 | 证据 |
|---|---|---|
| 外挂不停手动触发 F2 | ❌ 不可能 | F2 = GM 菜单指令，底层是 `GmActions` / `resetMobPosition`，**需要 GM 权限**。普通作弊号没有 GM 指令可用，更不会反复发。 |
| 服务端有循环一直吸 | ❌ 不存在 | `resetMobPosition` 全项目只有 **3 处调用**（F2×2 + GM 指令×1），**零定时/周期调用**；`MapleMap` 的 `TimerManager` 全是掉落/中毒/风筝/反应器/状态异常，**没有一处重定位怪物**。 |

**真实机制 = 客户端侧「封包钩子」，常驻在收包流上**：

1. 服务端按正常逻辑，把怪**生成在 wz 定义的原始刷怪点**（`SPAWN_MONSTER` 包带原始坐标），移动时由控制器客户端发 `MOVE_LIFE` 包（带当前坐标）。
2. 外挂 hook 住客户端**处理这两个入包的函数**，把包里的**坐标字段改写成的玩家脚下坐标**，再交给客户端正常解析。
3. 于是：
   - 服务端发来的位置被客户端"就地篡改" → 客户端在自己屏幕上把怪画在玩家身边 → 玩家攻击命中（MS 攻击按 objectID 校验，服务端基本盲信客户端报的伤害，不卡精确距离）。
   - **每只新刷的怪，只要它的 `SPAWN_MONSTER` 包流过，就被同一道钩子改写** → 全自动，不需要任何新触发。
4. 所谓"循环"其实**不是时间循环，是封包流循环**：只要有新包来，钩子就改。所以"怪死了→新怪在原位刷→又被吸"是这套机制的自然结果。

**⚠️ 重要更正（2026-09-24，用户纠错 + 源码坐实）：吸怪是「全图可见」的**

上面把吸怪归为"客户端视觉假象、只有开挂者自己看得到"是**错的**。用户在实际游戏里观察到：**全地图的人都看得到怪被吸到开挂者脚下**。源码完全支持这个观察——服务端**零校验地采信客户端报的坐标，再把原始报文广播给视野内所有人**：

| # | 证据（本仓库源码） | 含义 |
|---|---|---|
| 1 | `AbstractMovementPacketHandler.updatePosition`（`:166`）`target.setPosition(new Point(xpos, ypos + yOffset))` | 无条件采信客户端报的**绝对坐标**：没有距离校验、没有速度校验、没有与上次坐标的偏差校验 |
| 2 | `MoveLifeHandler`（`:167`）传进来的 `target` 就是那只 `MapleMonster` | ⇒ **服务端的权威坐标**被改成了客户端说的地方 |
| 3 | `MoveLifeHandler`（`:177`）`map.moveMonster(...)` | 伪造的坐标同步进地图对象表 |
| 4 | `MoveLifeHandler`（`:175`）`map.broadcastMessage(player, moveMonster(objectid, ..., startPos, slea, movementDataLength), serverStartPos)` | 把**客户端发来的原始移动字节**原样转发给视野内**所有玩家** |

⇒ 伪造坐标**既写进服务端权威状态、又被原样广播** ⇒ 全图所有人都看到怪聚到那人脚下。

**两种钩子方向必须分清**：

| 变体 | 钩在哪 | 服务端知道吗 | 别人看得到吗 |
|---|---|---|---|
| **发侧伪造**（经典 v83 vac／吸怪，主流） | 改写客户端**发给服务端**的 `MOVE_LIFE` 坐标 | **知道**（写进权威状态） | ✅ **全图可见** ← 实际观察到的就是这种 |
| **收侧改写**（纯本地视觉假吸） | 改写服务端**发来**的包坐标 | 不知道 | ❌ 只有自己屏幕 |

**一个对我们有利的推论**：既然怪被弄到玩家身边后**控制器客户端的本地 AI 照常在跑**（追人／攻击／小幅游走），那么"吸过来后在小范围不停移动"**是怪自身 AI 的自然产物**，外挂并没有算轨迹。⇒ 我们方案 A（不冻结 + 围栏兜底）方向正确：不冻结 → 怪自己的 AI 就会产生那个"活的"游走感，围栏只负责把跑远的拉回来。

**想在「服务端 legit」复现"持续吸"**：
- 没有"自动循环"这回事；要做只能**事件驱动**——要么保留 F2 手动触发，要么给脚本加一个"进图/杀怪回调里重新吸一次"的逻辑（仍是事件触发，不是真循环）。
- 真正"钉死+吸过来"一条龙，还是回到思路 A（冻结 + 召唤即定）。

> ⚠️ 客户端侧部分（钩子实现细节）是**对 v83 通用 vac 外挂架构的分析推断**，本服 `北冥` 客户端是二进制、无法读源码。**服务端侧结论（零校验采信客户端坐标 + 原样广播 ⇒ 全图可见）由本仓库源码实证**，见上方"重要更正"。

#### 11.1 `MapleMonster.java` —— 加冻结标志

public void setFrozen(boolean frozen) {

```

public void aggroUpdateController() {

```

#### 11.2 `MoveLifeHandler.java` —— 跳过位移应用（纵深防御）

Boolean aggro = monster.aggroMoveLifeUpdate(player);

public void spawnMonsterFrozen(int id, int x, int y) {

### §12.1 三轮优化（2026-09-22 晚）
- **第一轮**：吸怪落点从「脚下」改到「人物正右」（避免重叠被碰到）。`VACUUM_OFFSET_X` 常量 + `vacuumTargetPoint()`；`attractIfEnabled` 与开模式都用偏移落点。

- **第三轮**：`VACUUM_OFFSET_X` 由 100 改为 **200**（10 身位）。

**改动文件**：`MapleMap.java`（`VACUUM_OFFSET_X` 常量 + `vacuumTargetPoint()` 静态方法；`stopAutoAttract` 解冻强制 re-handoff；`attractIfEnabled` 用偏移落点）、`GmActions.java`（`toggleVacuum` 开模式用 `MapleMap.vacuumTargetPoint`）。

### §12.2 「围栏放养」——吸怪从「定死」改为「小范围游走」（★已实现 2026-09-24）
> ⚠️ 本节描述的「圈心跟着人物实时移动」已于同日改为「**固定圈心**」，见 **§12.3**。

**需求**：看别人的吸怪，怪被吸过来之后在很小的范围（左右共 4~5 个身位）内不停移动、不出圈，也不定住不动。

**为什么旧版是"定死"**（源码坐实）：`GmActions.toggleVacuum` 调 `m.setFrozen(true)`，而 `MoveLifeHandler`（`:154`）对 `isFrozen()` 直接 `return`（**连 `moveMonsterResponse` 都不回**）→ 控制器客户端收不到响应 → 不推进位置 → 怪钉死。这是 §11/§12 的刻意设计，**纯配置改不出来**。

**实现（方案 A：围栏放养）**——不冻结，让怪自身 AI 继续游走，服务端只在怪跑出半径时把它拉回来：

| 文件 | 改动 |
|---|---|
| `MapleMap.java` | 新增常量 `VACUUM_WANDER_RADIUS=100`（px，≈左右共 5 身位）、`VACUUM_FENCE_INTERVAL=400`（ms）、字段 `vacuumFenceTask`、方法 `startVacuumFence()` / `stopVacuumFence()`；`setAutoAttract(on)` 开=启围栏、关=停围栏；**`attractIfEnabled` 去掉 `setFrozen`**；`stopAutoAttract` 改为**只唤醒 `isAlive() && isFrozen()` 的怪**（不再无差别 remove+add controller，避免打断正常游走的怪） |
| `GmActions.java` | `toggleVacuum` **去掉 `setFrozen(true)`**，开模式只做「拉过来」 |
| `FaceExpressionHandler.java` | 提示语改为「开（怪围在身边小范围游走，击杀后新怪自动补吸；离图自动关）/ 关（怪恢复自由走动）」 |

**围栏任务怎么跑**（`TimerManager.register(task, VACUUM_FENCE_INTERVAL, VACUUM_FENCE_INTERVAL)`，每 400ms 一次）：

1. 若 `!autoAttract || attractor == null` → `stopVacuumFence()` 并退出（吸怪已关）；
2. 若吸引人**换图 / 下线 / 客户端为空** → `stopAutoAttract()` 并退出；
3. 否则取 `center = vacuumTargetPoint(attractor.getPosition())`（人物正右 200px），遍历全图怪：
   - 跳过已死亡的；
   - **只有 `getPosition().distanceSq(center) > 100²` 的怪**才 `resetMobPosition(new Point(center.x + Randomizer.nextInt(201) - 100, center.y))`；
   - ⇒ **按需拉回**（越界才发包），比"每 tick 全量重定位"省得多。

**验证（与编译产物逐字节比对）**：用 `javap -p -c` 对比重做后的 class 与 jar 中当时的 class，**45 个 class 全部一致**（含围栏任务匿名类 `MapleMap$10`）。⇒ 重做的源码与当时编译进产物的版本等同。

**已知代价**（用户已知悉并接受）：

- 不冻结 → **移动包量回升**（正是前几轮一直在削的"封包压力"），建议 `VACUUM_WANDER_RADIUS` 别调大、`VACUUM_FENCE_INTERVAL` 别调小、尽量在怪少的图用；
- 怪会**贴近玩家并攻击**（旧版冻结时不仅不动，连技能/攻击包都被拦；现在恢复成正常活怪）；
- 视觉上是「AI 自由游走 + 偶尔被"顿一下"拉回」，想更自然就让 AI 多干活、围栏少插手（半径放宽、间隔放长）。

**生效**：改 Java → 重编译 + 重打包 + **重启服务端**（铁律 1）；调参改两个常量同样要重编译。

### §12.3 「固定圈心」——围栏不再随人物移动（★已实现 2026-09-24 下午）

### §12.4 「软围栏」——越界不再「拽回圈心」，改为沿径向「按回圆周」（★已实现 2026-09-24 傍晚）

**需求**：希望怪"被限制在围栏内、无法越过围栏"，从而根本不存在"越界被拉回"这个动作。

**① 先厘清一个硬边界（重要认知，以后别再走弯路）**

083 里**怪物的位置是「控制器客户端」算的**：客户端把怪算好走位后发 `MOVE_LIFE`，服务端在 `AbstractMovementPacketHandler.updatePosition` 里**直接采信其坐标（零校验）**，只做「回 `moveMonsterResponse` + 广播 `moveMonster`」两件事。由此推出三条硬事实：

- 服务端**没有任何物理墙**能阻止客户端把怪算出圈 ⇒ **「怪绝对无法越界」在服务端层面做不到**。
- `moveMonster(...)` 包里**没有独立的终点字段**：轨迹是 `rebroadcastMovementList` 原样复制的**二进制字节流**（一串相对坐标）。想"逐包改坐标"必须重写该字节流 → 高风险，而且**控制者收不到这个广播**（`MoveLifeHandler:175` 用的是 `broadcastMessage(player, packet, serverStartPos)`，**不发给源**），改了对控制者本地预测也没用。
- 服务端**唯一**手段是事后搬运：`MapleMonster.resetMobPosition(Point)`（`MapleMonster.java:1325`）—— 卸控制器 → `setPosition` → 用**预置待机轨迹**广播 `moveMonster`（**无 source 版，含控制者**）→ 更新分区块索引 → 重发控制器。

⇒ 能做的是**「越界即被轻推回圆周」**（观感=贴着看不见的墙滑），做不到「零越界」。

**② 旧实现的「抽搐」根因**

```java
int nx = center.x + Randomizer.nextInt(201) - 100;   // 圈心附近「随机点」
m.resetMobPosition(new Point(nx, center.y));
```

越界后怪被扔到**圈心附近的一个随机位置**：位移可达上百 px、**方向完全随机**；它接着往外走、再被扔回来 → 观感就是"抽搐/瞬移"。

**③ 新实现（径向回推 radial clamp）**

| 位置 | 改动 |
|---|---|
| `MapleMap.VACUUM_FENCE_INTERVAL` | `400` → **`250`** ms（上限越界量随之从约 48px 降到约 30px） |
| `startVacuumFence` 任务体 | 落点改为沿「圈心 → 怪」射线与圆周的交点；另加 `dist < 1.0d` 防除零分支 |

```java
double radiusSq = (double) VACUUM_WANDER_RADIUS * VACUUM_WANDER_RADIUS;
Point mp = m.getPosition();
double distSq = mp.distanceSq(center);
if (distSq <= radiusSq) continue;                    // 圈内：一个字节都不发
double dist = Math.sqrt(distSq);
if (dist < 1.0d) continue;
int nx = center.x + (int) Math.round((mp.x - center.x) * VACUUM_WANDER_RADIUS / dist);
int ny = center.y + (int) Math.round((mp.y - center.y) * VACUUM_WANDER_RADIUS / dist);
m.resetMobPosition(new Point(nx, ny));
```

**④ 新旧对照**

| | 旧（跳回圈心随机点） | 新（径向按回圆周） |
|---|---|---|
| 位移量 | 最多 100px+ | **= 越界量**（约 24~30px，1~1.5 身位） |
| 位移方向 | 随机 | **顺着「圈心 → 怪」的射线**（怪原前进方向） |
| 观感 | 被拽回中心 → 抽搐 | 滑到墙边 → 被轻轻挡住 |
| 落点连续性 | 跳变 | 连续，严格落在圆周上 |

**⑥ 残余代价（已告知，用户本次选择「都不做」）**

### §12.5 「地面护栏」——落点必须先站得住（★已实现 2026-09-24 晚）

**问题（用户实测截图报）**：多层岩石图上，被围栏「按回」的怪有些**掉下平台**，而且会**一路往下掉不停**。

**根因（两层叠加）**

1. 径向回推**同时改 x 和 y**（`ny = cy + round((my-cy)*R/dist)`）—— 落点几何上正确，但**可能是半空**；
2. `resetMobPosition`（`MapleMonster.java:1325`）是**纯瞬移，完全不看脚下有没有地面**。

**⚠️ 连带死亡循环（关键）**：怪一旦掉到下层 → 与圈心的**垂直分量**变大（依旧算「越界」）→ 下一 tick 又被按到 **`ny ≈ cy + R`（圈心正下方约 97px）的悬空点** → 客户端让它继续下落 → **每 250ms 一次瞬移（3 个包），永不停止**。所以现象是「持续下坠」而不是一次掉落。

**改法（`MapleMap.java` 6 处 + `GmActions.java` 1 处，无新字段）**

新增一个常量 + 两个方法：

```java
private static final int VACUUM_MAX_DROP = 60;   // 允许的最大高低差（≈3 身位）

/** 落点必须站得住：取 target 脚下地面；脚下无地面 或 地面与 from 高低差 > VACUUM_MAX_DROP → 返回 null */
public Point safeVacuumLanding(Point from, Point target) {
    Point land = calcPointBelow(new Point(target.x, target.y - 1));
    if (land == null) return null;                                        // 悬崖外/深渊
    if (from != null && Math.abs(land.y - from.y) > VACUUM_MAX_DROP) return null;   // 在别的一层
    return new Point(land.x, land.y - 1);
}

/** 圈心也要安全：优先「人物正右 200px」的地面，那里悬空就退到人物脚下的地面 */
private Point vacuumCenterFor(Point origin) { ... }
```

| # | 位置 | 改动 |
|---|---|---|
| 1 | `startVacuumFence` 围栏回推 | 算完 `(nx, ny)` 后过 `safeVacuumLanding(mp, ...)`，**null 就 `continue`**（不动这只怪） |
| 2 | `attractIfEnabled` 新刷怪落点 | 同上；圈心附近的点站不住 → **退一步落圈心**；都站不住 → 留在刷怪点 |
| 3 | `setAutoAttract` 圈心 | `vacuumTargetPoint(...)` → **`vacuumCenterFor(...)`**（圈心也吸附到地面；右侧悬空则退到人物脚下） |
| 4 | `GmActions.toggleVacuum` 初始搬运 | 圈心站不住 → **一只都不搬**（提示 + 回滚开关）；校验时 **`from` 传 `null`** = 不比较层级 |

**第 4 处的 `from = null` 很关键**：不比较层级 ⇒ 已经掉到下面那层的怪也能被这次搬运**拉回圈心所在层**。所以「关一次吸怪再开」就是把掉落怪救回来的手段。

**`calcPointBelow` 是项目现成方法**（`MapleMap.java:489`，private；`getPointBelow`:1890 是 public 包装）：`footholds.findBelow(p)`（`MapleFootholdTree:162`）找**下方**最近 foothold，**无则返回 null**；返回 `new Point(传入的x, 地面y)` —— **只修正 y**。`spawnMonsterOnGroundBelow`:1856 的既有惯例 = `pos.y-1` → `calcPointBelow` → `y--`，本方法照抄。

**顺带治好的**：加了「跨层就跳过」之后，**掉落后的无限下坠自动停止**（那类怪与圈心垂直差 > 60px → 永久跳过）。

1. `deploy_classes.py` 编译 2 文件，无 error（仅既有 unchecked 警告）；
2. `patch_jar.py` → 条目 **2031 → 2031**、jar **3,685,602 B**（本次生成 41 个 class）；
3. jar 内 **39 个 class（含 `MapleMap` 全部内部类）与 `out\production` md5 逐一相同**；新方法 `safeVacuumLanding` / `vacuumCenterFor` 已在 `MapleMap` 字节码中；

### §12.6 护栏的「层级比较」参照物搞错了 —— 新刷的怪吸不过来（★已修 2026-09-24 夜）

**问题（用户实测报）**：吸完怪、打死怪之后，**补刷出来的新怪不再被吸到圈心**，全散在各自的刷怪点上；只有首次按 X 开启时那一次搬运是好的。

**根因：地面护栏的层级比较拿错了参照物。**

`safeVacuumLanding` 原本签名是 `safeVacuumLanding(Point from, Point target)`，用**怪自己的 y** 当参照：

```java
if (from != null && Math.abs(land.y - from.y) > VACUUM_MAX_DROP) return null;
```

- 首次开启的搬运走 `GmActions.toggleVacuum`，`from` 传 **null** ⇒ 不比较层级 ⇒ 全部吸成功 ✅
- 新刷的怪走 `attractIfEnabled`，`from` = `m.getPosition()`（= 它在 wz 里的**刷怪点**）⇒ 一旦刷怪点与圈心不在同一层（高低差 > 60px），**永久返回 null**；
- 更糟的是**围栏回推也被它卡死**：`safeVacuumLanding(mp, 圆周点)` 里的 `mp` 就是这只怪，它已经在圈外、位置本来就在别的层 ⇒ 每次 tick 都被判「异层」→ `continue` → **这只怪从此永远在围栏之外**。

一句话：**拿怪当前的 y 当参照，等于给「怪已经不在圈内」这件事判了死刑。**

**改法（只动 `MapleMap.java`，4 处）**

1. 签名换成 `safeVacuumLanding(Integer refY, Point target)`（`refY == null` = 不做层级比较；`Integer` 而非 `int`，这样 `GmActions` 里原有的 `safeVacuumLanding(null, pos)` 不用改）；
2. **围栏回推**（`startVacuumFence`）：参照传 **`center.y`（圈心）**，不是怪当前的 y；
3. 围栏回推的兜底：圆周点若正好悬在深坑上（返回 null）→ **再退一步 `safeVacuumLanding(null, center)`** 按回圈心，保证「只要圈心站得住，怪就回得来」；
4. **新刷怪吸怪**（`attractIfEnabled`）：全部传 **`null`**（不比较层级）；只有「脚下真的没有地面（悬空）」才退回圈心，圈心也站不住才留在刷怪点。

> 设计原则：**该拉的一律拉过去（落地由 `calcPointBelow` 保证是实地面），护栏只拦「落点是悬空的」这一件事**，不再替怪判断「你该在哪一层」。

**顺带调小的**：`VACUUM_WANDER_RADIUS` **100 → 50**（用户手动改），围栏内自由游走范围变成圈心左右各 50px，新怪落点散布也同步变小 → 新怪更集中在圈心。

**验证（三重）**

1. `deploy_classes.py` 编译 `MapleMap.java` + `GmActions.java`，无 error；
2. `patch_jar.py`：`out\production` 与 jar **两份**都更新（`MapleMap.class` / `GmActions.class` **md5 逐一相同**），jar 条目 2031 → 2031；
3. **反编译确认传参**：`javap -p -c MapleMap$10` 中回推调用前是 `aload_1; getfield Point.y; invokestatic Integer.valueOf` ⇒ 传的是**圈心的 y**（不是 `mp`）；兜底那次是 `this$0; aconst_null; aload_1` ⇒ 传 `null` + `center`。`MapleMap.class` 里 `attractIfEnabled` 两处调用前都是 **`aconst_null`** ⇒ 新怪吸怪不再比较层级。`access$` 编号仍 **23 定义 = 23 引用**，无未定义引用。
