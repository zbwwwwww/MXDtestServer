## 2. 最重要的认知修正：「吸怪」其实是两件完全不同的事

这是本次调研最值钱的一条，直接决定实现方案：

| 方式 | 服务端做什么 | 客户端会照做吗 | 现状 |
|---|---|---|---|
| **移动已有怪**<br>`mob.resetMobPosition(pos)` | 发 `moveMonster` 包改位置 | ⚠️ **不一定** —— 怪的位置本来由客户端驱动（`MoveLifeHandler`），服务端只是转发 | 已接 F2 键，**至今未实测通过** |
| **召唤新怪到脚下**<br>`map.spawnMonsterOnGroundBelow(id,x,y)` | 发 `spawnMonster` 包 | ✅ **一定** —— 怪"出生"就在那，客户端没有反驳余地 | 菜单 `#L19#` 已在用，**已验证** |

⇒ **想让"隔壁图的怪出现在我脚下"，用「复制+在脚下召唤」比「搬位置」可靠得多。**
`resetMobPosition` 那条路（全项目零调用方）能不能生效，还是个悬案。

| 档 | 范围 | 量级 | 备注 |
|---|---|---|---|
| **1a 左右出口** | 只 `pt=2` 的图（通常 2~3 张） | 小 | **推荐先做这个**：精准、贴"左右"的直觉、量大不了 |

**实现要点（1a）**：
1. 遍历 `getPortals()`，筛 `getType() == 2`（`MaplePortal.MAP_PORTAL`）
2. `getTargetMapId()` 去重、排除 `999999999`
3. 对每张目标图取怪 → **在脚边左右散开召唤**

如果那张图从没被访问/生成过，返回可能是**空的** —— 不是 bug，是懒加载。
所以 1a/1b 要准备好"该图暂时没有怪"的提示，或者走**读 wz `life` 节点**的兜底（复杂一档）。

## 10. 原理：吸过来的怪为什么会乱跑？外挂"定怪"是怎么做到的？

> 用户晚上的疑问：F2 吸怪后，怪会散开、左右跑、到处跑；而别人外挂吸怪时，怪只在很小范围动甚至完全不动。差异在哪？

### 10.1 先看清 F2 吸怪到底干了什么

`gm_menu.js:1442` 调 `mob.resetMobPosition(pos)`，服务端实现是 `MapleMonster.java:1325`：

```java
public void resetMobPosition(Point newPoint) {
    aggroRemoveController();                              // ① 解除当前控制器
    setPosition(newPoint);                                // ② 服务端把怪瞬移到脚下
    map.broadcastMessage(moveMonster(... getIdleMovement() ...)); // ③ 广播"怪移动了"（idle 动画，不立即走动）
    map.moveMonster(this, this.getPosition());            // ④ 更新服务端坐标 + 可见性
    aggroUpdateController();                              // ⑤ 重新分配控制器（立刻又对你 aggro）
}
```

**关键点**：`resetMobPosition` 只是"瞬移 + 重新挂上 AI"。它**没有、也不可能让怪停下来**——
因为第 ⑤ 步 `aggroUpdateController()` 让怪重新认你做主人，怪的 AI 立刻开始**追你**。

### 10.2 怪的"走动"到底谁在驱动？（这是核心）

**服务端自己不模拟怪物行走**。`MapleMonster` 里的 `TimerManager` 只用于技能冷却 / 掉落 / 木偶仇恨（`MapleMonster.java:772/831/2181`），
**没有任何"怪物巡逻/追击"的定时线程**。怪的位移来自：

1. 某玩家 aggro 了这只怪 → 该玩家的客户端成为"控制器"（`MapleCharacter.controlMonster`，`:1970`）。
2. 客户端本地的怪物 AI 算出"该往哪走"，发出 `MOVE_LIFE` 包（`RecvOpcode.MOVE_LIFE` → `MoveLifeHandler`）。
3. `MoveLifeHandler.java:163/173`：`updatePosition(slea, monster, -2)` 把**客户端报上来的位移**直接套到怪的服务端坐标，
   再 `map.broadcastMessage(moveMonster(...))` **转发给其他人**。

⇒ **服务端对怪物移动是"盲信客户端 + 纯转发"**。客户端说往哪走、走多远，服务端就信、就广播。

### 10.3 所以"乱跑"和"定怪"是同一件事的两面

| 现象 | 谁在动怪 | 服务端看到什么 |
|---|---|---|
| F2 吸怪后到处跑 | 你的客户端对脚下这些怪 aggro 了，本地 AI 让它们**追你** → 不断发 `MOVE_LIFE` | 收到位移包 → 应用 + 转发 → 怪就游走、散开 |
| 外挂"定怪" | 外挂**劫持了**它作为控制器的那只怪的移动生成：把"追你"的位移**替换成"原地不动 / 极小抖动"** | 收到的全是"几乎不动"的包 → 应用 + 转发 → **所有人看到怪钉死** |

**结论**：外挂的"定怪"不是服务端功能，是**纯客户端/网络层技巧** —— 它控制了怪的 `MOVE_LIFE` 包内容，
把正常的追击位移改成"零位移"或"小幅抖动"。因为服务端盲信控制器客户端，所以全服都看到怪不动。
这就是你看到的"很小范围移动（小幅抖动）"和"完全不动（零位移）"两种表现的来源。

### 10.4 那我们服务端这边能不能" legit 地定怪"？

能做，但需要**改 Java + 重编译**（不走纯脚本路线），三种思路：

| 思路 | 做法 | 改动量 | 评价 |
|---|---|---|---|
| **A. 冻结标志位** | 在 `MapleMonster` 加 `frozen` 字段；`MoveLifeHandler.java:163` 处若 `monster.isFrozen()` 则跳过 `updatePosition`（只更新朝向），并把 `aggroUpdateController` 改成不追玩家 | 中（改 2 个文件 + 吸怪脚本里置位） | **最干净**，吸完即钉死，且不打客户端包 |
| **B. 关闭移动动画** | 召唤时把该怪 `MapleMonsterStats` 的 `animationTimes` 去掉 `move`/`fly` → `isMobile()` 返回 false（`MapleMonsterStats.java:140`） | 中（重载 stats） | 怪彻底不走动画，但会"飘"在原地，且是 per-类型 |
| **C. 定时回拉** | 吸怪后起一个定时器（如每 200ms）反复 `resetMobPosition` 钉在脚下 | 小（脚本 + 一个 Timer） | 会和客户端 `MOVE_LIFE` 打架、画面闪烁，**不推荐** |

> 思路 A 最适合配合"召唤点名"做成"吸过来 + 钉死"一条龙。但属于**新功能**（用户尚未要求），
> 等你想做再单独立项、走"先给 diff 再动手"流程。
> ⚠️ **A 与 C 互斥、不叠加**：A = 源头不让坐标变（`MoveLifeHandler` 跳过 `updatePosition`，根本不发移动包）；C = 坐标被客户端改了、每 200ms 拉回。A 生效时坐标本不变，C 拉的是空操作；C 生效时 A 多余。两者同开只浪费资源、行为还可能打架。**二选一，推荐 A**。

### 10.5 一句话总结

- **乱跑**：F2 只瞬移、不锁 AI，怪被你的客户端驱动着追你 → 自然散开游走。
- **定怪**：外挂在它作为控制器的一端，把怪的位移包改成"零/极小"，服务端盲信 → 全服看到不动。
- **想在服务端 legit 复现**：思路 A（冻结标志 + MoveLifeHandler 跳过位移）最稳，但要改 Java。

### 10.6 外挂的「连续自动吸怪」是怎么实现的（2026-09-22 追加）

**现象**：怪被打死后，原位置刷新新怪，外挂又自动把新怪吸过来——像有循环在一直吸。

**先排除两个错误假设（均有服务端代码铁证）**：

| 假设 | 是否成立 | 证据 |
|---|---|---|
| 外挂不停手动触发 F2 | ❌ 不可能 | F2 = GM 菜单指令，底层是 `GmActions` / `resetMobPosition`，**需要 GM 权限**。普通作弊号没有 GM 指令可用，更不会反复发。 |
| 服务端有循环一直吸 | ❌ 不存在 | `resetMobPosition` 全项目只有 **3 处调用**（F2×2 + GM 指令×1），**零定时/周期调用**；`MapleMap` 的 `TimerManager` 全是掉落/中毒/风筝/反应器/状态异常，**没有一处重定位怪物**。 |

**真实机制 = 客户端侧「封包钩子」，常驻在收包流上**：

1. 服务端按正常逻辑，把怪**生成在 wz 定义的原始刷怪点**（`SPAWN_MONSTER` 包带原始坐标），移动时由控制器客户端发 `MOVE_LIFE` 包（带当前坐标）。
2. 外挂 hook 住客户端**处理这两个入包的函数**，把包里的**坐标字段改写成的玩家脚下坐标**，再交给客户端正常解析。
3. 于是：
   - 服务端发来的位置被客户端"就地篡改" → 客户端在自己屏幕上把怪画在玩家身边 → 玩家攻击命中（MS 攻击按 objectID 校验，服务端基本盲信客户端报的伤害，不卡精确距离）。
   - **每只新刷的怪，只要它的 `SPAWN_MONSTER` 包流过，就被同一道钩子改写** → 全自动，不需要任何新触发。
4. 所谓"循环"其实**不是时间循环，是封包流循环**：只要有新包来，钩子就改。所以"怪死了→新怪在原位刷→又被吸"是这套机制的自然结果。

**对服务端架构的启示（为什么这招在服务端测不出来）**：
- 服务端看到的怪物坐标**始终是原始刷怪点**（因为客户端从没把"被吸到玩家身边"这件事回报给服务端——`MOVE_LIFE` 是客户端本地 AI 算的，外挂连这个都改成"零/极小位移"或直接不发）。
- 所以服务端日志里怪一直好好的在刷怪点，全服其他人（没开挂的）也看到怪在原位——**只有开挂者自己看到怪聚在脚下**。这就是纯客户端技巧的本质。

**想在「服务端 legit」复现"持续吸"**：
- 没有"自动循环"这回事；要做只能**事件驱动**——要么保留 F2 手动触发，要么给脚本加一个"进图/杀怪回调里重新吸一次"的逻辑（仍是事件触发，不是真循环）。
- 真正"钉死+吸过来"一条龙，还是回到思路 A（冻结 + 召唤即定）。

> ⚠️ 客户端侧部分（钩子实现）是**对 v83 通用 vac 外挂架构的分析推断**，本服 `北冥` 客户端是二进制、无法读源码；以上结论的**服务端侧**（无循环、F2 需 GM 权限）由本仓库源码实证。

### 11. 思路 A（冻结/定怪）具体实现方案（用户问"怎么改、效果怎样"）

**改动范围**：2 个 Java 文件（核心）+ 1 个脚本集成点（做"召唤即钉死"）。**改 Java → 必须重编译 + 重启服务端**（铁律 1）。

#### 11.1 `MapleMonster.java` —— 加冻结标志

字段区（`private boolean fake = false;` 附近，≈ 行 99）加：
```java
private boolean frozen = false;
```
getter/setter（建议放在 `isMobile()` 行 1047 之后）：
```java
public void setFrozen(boolean frozen) {
    this.frozen = frozen;
    if (frozen) {
        aggroRemoveController();   // 立即丢掉控制器 → 客户端不再发 MOVE_LIFE
    }
}
public boolean isFrozen() {
    return frozen;
}
```
`aggroUpdateController()`（行 1969）开头加守卫，让冻结怪永不被认领为控制器：
```java
public void aggroUpdateController() {
    if (frozen) return;            // ← 新增：冻结怪不追玩家、不发移动包
    MapleCharacter chrController = this.getActiveController();
    ...
}
```
> 依据：`aggroRemoveController()`（行 1886，public）不依赖 map，冻结前（怪物还没上图）调用也安全。

#### 11.2 `MoveLifeHandler.java` —— 跳过位移应用（纵深防御）

`aggro` 检查之后（行 152 之后）加：
```java
Boolean aggro = monster.aggroMoveLifeUpdate(player);
if (aggro == null) return;
if (monster.isFrozen()) return;   // ← 新增：冻结怪的移动包直接丢弃，不套坐标、不广播
```
> 因为 11.1 已让 `aggroUpdateController` 变 no-op，客户端本就不会发 `MOVE_LIFE`；这里再拦一道，兜底"冻结前已有控制器"等漏网包。核心落点在 `updatePosition(slea, monster, -2)`（行 163）—— 冻结时根本不执行，服务端坐标永不变，`map.moveMonster` 也不广播。

#### 11.3 召唤点名集成（吸+钉一条龙）

`AbstractPlayerInteraction.java`（行 992 之后）加 frozen 变体：
```java
public void spawnMonsterFrozen(int id, int x, int y) {
    MapleMonster monster = MapleLifeFactory.getMonster(id);
    monster.setPosition(new Point(x, y));
    monster.setFrozen(true);          // 出生即冻结
    getPlayer().getMap().spawnMonster(monster);
}
```
召唤点名脚本把 `cm.spawnMonster(id, x, y)` 换成 `cm.spawnMonsterFrozen(id, x, y)` 即可。
（若也想让现有 F2 吸过来就钉死：在 `gm_menu.js:1442` 的 `resetMobPosition` 之后加 `mobs.get(i).setFrozen(true);` 即可。）

#### 11.4 最终效果

| 行为 | 表现 |
|---|---|
| 召唤/吸到脚下 | **完全静止**：不游走、不追人、不散开、不闪 |
| 攻击 / 掉血 / 死亡 | 照常，就是个"固定靶子" |

⚠️ 站桩怪仍会造成**接触伤害**（贴上去被碰掉血）——但你秒它，无所谓。
