# 技能 · 释放动画锁与「即时释放」（2026-09-24）

## 1 · 现象

用主教 4 转 **圣光普照**（`Bishop.GENESIS` = **2321008**，走 `wz\Skill.wz\232.img.xml`）后，
人物有**约 3 秒不能动**，期间也没法再次施放 —— 想改成「释放完立刻能动、能立刻再放」。

## 2 · 链路与根因

| 环节 | 事实 |
|---|---|
| 释放路径 | 圣光普照是**魔法攻击** ⇒ 走 `net\server\channel\handlers\MagicDamageHandler.java`（不是 `SkillEffectHandler`，后者只处理 BIG_BANG / HURRICANE 等白名单） |
| 广播 | `MagicDamageHandler:62` `chr.getMap().broadcastMessage(chr, packet, false, true)` = `repeatToSource=false` ⇒ **本人根本不收这个 attack 包** |
| 动画 | 技能特效是**客户端本地预测播放**的（约 3 秒），本地播完才解锁 ⇒ **服务端"不发包"也拦不住**（本地早就播了） |
| 服务端 wz 数据 | `wz\Skill.wz\232.img.xml` 的 `2321008/level/N` 只有 `mpCon` / `mad` / `lt` / `rb` / `mobCount` / `mastery` —— **没有 `cooltime`，也没有 `effect`** ⇒ 服务端既控制不了动画时长、也本来就没有冷却 |
| 服务端的冷却机制 | `MagicDamageHandler:66~73` 用 `effect_.getCooldown() > 0` 才 `addCooldown`；这里 `getCooldown() == 0` ⇒ **当前其实没有任何冷却** |

⇒ 所谓「3 秒不能再用」，纯粹是**客户端那段本地特效动画**的副作用，不是服务端逻辑。

## 3 · 唯一的杠杆：CANCEL_SKILL_EFFECT (0xBF)

项目里早有先例：`CancelBuffHandler:55` 在取消 BIG_BANG / HURRICANE / RAPID_FIRE / FIRE_BREATH
这些**长特效技能**时，用的就是

```java
MaplePacketCreator.skillCancel(from, skillId)   // SendOpcode.CANCEL_SKILL_EFFECT(0xBF)
```

这里有个**容易踩的陷阱**：`CancelBuffHandler` 那条路能成，是因为 BIG_BANG 这类技能**有服务端 effect 驱动**
（`SkillEffectHandler` 白名单会给全图广播 `skillEffect`），0xBF 是去摘掉"服务端播的那个 effect"。

而圣光普照 **不属于这一类**（见 §3.1），所以"有先例"不代表能照搬。

### 3.1 ★ 实测结论：单发 0xBF 无效（2026-09-24 晚，用户实测"还是不能移动、也不能连按"）

翻 `Skill.wz\232.img.xml`，`2321008` 的 level 数据只有：

```
<string name="hs" value="h1"/>        <int name="mpCon" value="2100"/>
<int name="mad" value="430"/>          <vector name="lt" x="-400" y="-350"/>
<vector name="rb" x="400" y="250"/>    <int name="mobCount" value="15"/>
<int name="mastery" value="10"/>
```

**没有 `effect` 节点，也没有 `cooltime`** ⇒ 服务端从头到尾没为它发过 effect 包 ⇒ 客户端那段约 3 秒的光柱
是**客户端内建动画**，压根不在 0xBF 的管辖范围（0xBF 只能摘"服务端 effect 播出来的那个"）。
这也顺带解释了为什么之前"查不到 cooltime"——它本来就没有任何服务端侧限制，3 秒锁是**纯客户端行为**。

## 5 · 为什么服务端改不了：三条路都被堵死

| 想走的路 | 为什么堵死 |
|---|---|
| 不把 attack 包发给他本人 | `MagicDamageHandler` 广播用的是 `repeatToSource=false`，**本人本就不收**自己的攻击包 |
| 用 0xBF 取消特效提前解锁 | 0xBF 只能摘"服务端 effect 播出来的特效"；2321008 服务端**从没发过 effect**（wz 里没 effect 节点） |
| 用 `enableActions()` 解卡 | 它对应 `STAT_CHANGED` 处理，只解得到 effect 那类锁；攻击动画锁不归它管 |
| 靠 wz 的 `cooltime` 加硬冷却 | wz 里 `2321008` **没有 cooltime**，服务端对它本来就零限制 |

⇒ 结论：**3 秒锁是客户端 exe 里的一个硬编码常数，服务端任何包都动不了它。**

### 6.3 ★ 真锁在 0x556d49

在 `0x556c46`（`cmp ?, 2321008`）那条分支随后的 straight-line 块里：

```
00556d43  mov dword ptr [ecx+0x2b28], eax     ; 技能结构 +0x2b28 = 起点时间

00556d4e  mov  dword ptr [ecx+0x2b2c], eax    ; +0x2b2c = 到期时间
00556d54  jmp  0x556d9a
```

### 6.4 闭环验证：这两个字段确实被「判锁」读走

判定函数 `0x557bf8`（同区域）：

```
00557bf8  cmp dword ptr [esi+0x2b28], edi     ; 起点
00557bfe  je   0x557c10
00557c00  mov  ecx, [esi+0x2b2c]
00557c06  sub  ecx, eax        ; eax = 当前时间
00557c08  test ecx, ecx
00557c0a  jg   0x558130        ; 到期时间 - 现在 > 0 ⇒ 仍在锁内 ⇒ 退出
```

解锁 + 重新登记窗口的函数 `0x54e5e5`（**全 exe 只有 1 个调用者**，在 `0x54b9e7`）：

```
0054e5e9  call 0x587257                  ; eax = 当前时间
0054e5ee  cmp dword ptr [esi+0x2b18], 0  ; 是否正在放技能
0054e5f7  je   0x54e68f                  ; 空闲 → 直接返回
0054e5fd  mov  eax, [esi+0x2b28]
0054e603  sub  eax, ebx                  ; 起点 - 现在
0054e607  jg   0x54e68f                  ; 未到期 → 保持锁
0054e64b  and  dword ptr [esi+0x2b18], 0 ; ★★ 到期 ⇒ 解锁
0054e676  mov  dword ptr [esi+0x2b28], ebx
0054e67c  add  ebx, 0x258                ; 600 ms
0054e688  mov  dword ptr [esi+0x2b2c], ebx ; 重新登记 600 ms 新窗口
```

⇒ 结构语义确认为 **[+0x2b18] 正在放技能 / [+0x2b28] 起点 / [+0x2b2c] 到期**，
而 `add eax,3000` 是决定到期时间的那一句。**改它才对。**

### 7.1 改 exe 的四个致命坑（本轮全踩过一遍）

1. **指令长度必须逐站点算。** `05 <imm32>` 是 **5 字节**，`c7 45 <modrm> <imm32>` 是 **7 字节**。
   图省事统一按 7 字节写，会把 exe 截短 2 字节、其后代码全部错位 —— 本轮真把文件写坏过一次。
   教训：**写之前先算 `len`，写之后立刻校验文件大小 + md5。**
2. **备份文件名不能用 `basename`。** Windows 大小写不敏感，
   `Maplestory.exe` 与 `maplestory.exe` 是**同一个文件**，后写的备份会覆盖先写的，
   还原时就把错内容写回去了。备份目录要按内容区分，或干脆用完整路径。
3. **前缀比对的切片长度要对齐。** 拿 `b[off:off+2]` 去比 3 字节前缀 `c74508` 永远不匹配，
   站点会被判成"意外字节"而跳过——表现为"改了但没生效"。
4. **取证要用未打补丁的原版。** 已改过的 exe 代码流变了，反汇编出来的上下文会把你带偏。
