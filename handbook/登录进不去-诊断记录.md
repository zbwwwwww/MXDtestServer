## 一、先回答：改 `drop_data.chance` 不会导致进不去

**不会。** 有代码依据。

`MapleMap.java:644-658`：

```java

    ...
    for (final MonsterDropEntry de : dropEntry) {
        float cardRate = chr.getCardRate(de.itemId);
        int dropChance = (int) Math.min((float) de.chance * chRate * cardRate, Integer.MAX_VALUE);

        if (Randomizer.nextInt(999999) < dropChance) {
```

- `chance = 300000000` ⇒ `dropChance` 被 `Math.min(..., Integer.MAX_VALUE)` 夹住，**不会溢出**；
- 判定 `nextInt(999999) < 300000000` **恒为真** ⇒ 那件物品**100% 掉落**（游戏平衡问题）；
- 没有循环、没有数组下标、没有除零 ⇒ **不可能抛异常，更不可能挂住登录**；
- 而且 `drop_data` 是**按怪物惰性读取**的（杀怪时才读，读一次进内存缓存），**和登录流程完全没有交集**。

顺带一句：`drop_data` 的 `chance` 是**百万分比**（`1000000` = 100%，源码 `MapleMap.java:765` 有注释 `int chRate = 1000000; // guaranteed item drop`）。
但要注意 `reactordrops` 表的语义**正好相反**（`chance` 是分母，越小越容易掉）。

## 二、真正的发现（三条）

### 发现 1：登录流程的异常被彻底吞掉，什么日志都不留 ⚠️ 最重要

`PlayerLoggedinHandler.java:439`：

```java
} catch(Exception e) {
    e.printStackTrace();     // ← 只打到 IDEA 控制台，不落任何日志文件
} finally {
    c.releaseClient();
}
```

而且这个方法里有 **6 处静默踢人**（`c.disconnect(true, false)`，连一行日志都没有）：

| 行号 | 条件 |
|---|---|
| 114 | `world` 取不到 |
| 124 | `channel` 取不到（连频道 1 也不存在） |
| 136 | 拿不到登录会话的 HWID |
| 149 | `validateCharacteridInTransition` 失败 |
| 163 | `loadCharFromDB` 之后 `player` 仍为 null |
| 196-197 | **`getLoginState() == 2`（账号已是登录态）→ 直接踢，不解释** |

**结论：一旦这里出问题，服务端"一声不吭"，客户端就是"双击没反应"。** 这就是为什么翻遍 `logs/` 只有 3 个今天的文件、且没有一个和登录相关。

另外 `MapleClient.getLoginState()`（`MapleClient.java:825`）**读的是数据库**（`SELECT loggedin, lastlogin, birthday FROM accounts`），不是内存字段：

- `state == 1`（SERVER_TRANSITION）且 `lastlogin + 30 秒` 已过期 ⇒ 视为未登录；
- `state == 1` 且没过期 ⇒ **顺手把 DB 改回 0** 再返回 1；
- `state == 2`（LOGGEDIN）⇒ 上层直接静默踢人。

⇒ **只要账号卡在 `loggedin = 2`，之后每次双击角色都会被静默踢掉**，现象就是"永远进不去、毫无提示"。

### 发现 2：HikariCP 连接池从未被初始化（真 bug）

`DatabaseConnection.java:19-94`：

```java
private static HikariDataSource ds;

public static Connection getConnection() throws SQLException {
    if(ds != null) { ... ds.getConnection(); }
    // 否则每次 new 一条连接（最多连打 3 次，第 3 次失败就抛异常）
    return DriverManager.getConnection(DB_URL, DB_USER, DB_PASS);
}

public DatabaseConnection() {         // ← 池在这里创建
    ...
    if(YamlConfig.config.server.DB_CONNECTION_POOL) { ds = new HikariDataSource(config); }
}
```

**但全项目 `new DatabaseConnection()` 零调用** —— 构造函数从来没被执行过 ⇒ `ds` 永远是 `null` ⇒
**每条 SQL 都新建一条 TCP 连接**（虽然 `config.yaml` 里 `DB_CONNECTION_POOL: true`）。

实测佐证：MySQL `PROCESSLIST` 里**没有任何常驻连接**（池应该是 10~30 条常驻），而 `3306` 端口在 2 分钟内产生了约 715 个 `TIME_WAIT`。

### 发现 3：本机临时端口池已被打满（当场复现）

```
netsh int ipv4 show dynamicport tcp
  起始端口: 49152   端口数: 16384        ⇒ 可用端口 49152~65535，共 16384 个

netstat -ano -p tcp 统计
  TIME_WAIT: 17999   (!!)
  CLOSING:   150
  LAST_ACK:  27
  ESTABLISHED: 94
```

**TIME_WAIT 17999 ≥ 可用端口 16384** ⇒ 本机**开不出新的 TCP 连接**。
当场复现：诊断过程中我连 MySQL 被拒两次 —— `ERROR 2003 (HY000): Can't connect to MySQL server on '127.0.0.1' (10048)`（10048 = `WSAEADDRINUSE`，本地无端口可分配）。
同时 `java.exe (PID 31408)` 出现 `SYN_SENT=2`（服务端自己也连不出去）。

**制造这 1.8 万个连接的不是游戏**，按远端端口归类：

| 远端端口 | TIME_WAIT 数量 |
|---|---|
| 443（HTTPS） | **11316** |
| 80（HTTP） | 1906 |
| 8081 | 1414 |
| 3306（MySQL） | 715 |
| 50551 / 53149 / 53258 | 683 / 639 / 264 |

来源 IP 有两个：`192.168.0.115`（本机 WLAN）和 `192.168.0.113`（本机另一块网卡/虚拟网卡）。
活跃到 443 的进程只有 `WorkBuddy.exe`（CEF 子进程），但**绝大多数是 TIME_WAIT（PID 0，已无进程可归属）**。

⇒ 只要端口池处于打满状态，服务端**随机地**开不出数据库连接。而随机失败 + 异常被吞 = **偶发的"双击没反应"**。

## 三、上一轮的一个错误结论（已纠正）

上一轮我曾判断 `skills` 表里 `skillid = 12` 是脏数据、会让 `SkillFactory.getSkill(12)` 返回 null 并空指针崩溃。

**这个判断是错的。** 实测（真 JVM 调 `SkillFactory.loadAllSkills()` 后用反射导出全部技能 ID）：

```
已加载技能总数: 535
最小 10 个 ID: [8, 12, 100, 1000, 1001, 1002, 1003, 1004, 1005, 1006, ...]
map 里是否存在 key=12 : true
getSkill(12) -> 非 null
```

`wz/Skill.wz/000.img.xml`（初心者职业文件）里**确实注册了 ID = 8 / 12 / 100 / 1000~1031 / 9000~9002** 这些短 ID 技能。
`PlayerLoggedinHandler:355` 的 `10000000 * getJobType() + 12` 在 job=100 时算出来正是 `12`，属于**合法命中**（它是个 0 级的初心者技能，无害）。

> 上一轮那个手写的 XML 层级扫描器有 bug，漏掉了这些短 ID，导致误判。教训：**能跑真代码就别手写解析器。**
