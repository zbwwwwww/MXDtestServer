## 一、为什么现在会差 16 小时（三层机制）

| 层 | 事实 | 证据 |
|---|---|---|
| MySQL | 会话时区 = `SYSTEM` = **中国标准时间（+08:00）** | `SELECT NOW(), UTC_TIMESTAMP()` → `18:52:58` / `10:52:58`，正好差 8h |
| 驱动 | Connector/J **5.1.6**，URL 里**没有** `serverTimezone` ⇒ `useLegacyDatetimeCode` 默认 true ⇒ 用 **JVM 默认时区**把 `Timestamp` 化成字面量发给 MySQL | 探针 [B] |
| 应用 | JVM 默认时区被 `Server.java:763` 设成 **GMT-8**（读 `config.yaml:308` 的 `TIMEZONE`） | `TimeZone.setDefault(...)` |

**探针实测（同一个"此刻"，真实 UTC = 2026-09-21 10:54:05）**：

```
JVM 时区 = GMT-8    →  驱动发给 MySQL 的字面量: '2026-09-21 02:54:05'
JVM 时区 = GMT+8    →  驱动发给 MySQL 的字面量: '2026-09-21 18:54:06'   ← 和 MySQL 自己的 NOW() 完全一致
```

### 关键：一进一出正好抵消，所以程序一直没坏

| | 写入 | 读出 |
|---|---|---|
| GMT-8（现状） | 发 GMT-8 字面量 `08:48`，MySQL 当成 +08:00 的 `08:48` ⇒ **存的瞬时比真实早 16h** | 把 `08:48` 又按 GMT-8 解释 ⇒ **应用内存里是对的** |
| GMT+8（改后） | 发北京时间字面量 ⇒ **存的瞬时正确** | 按 GMT+8 解释 ⇒ 新数据正确 ✅<br>**但旧数据会被读成比真实早 16 小时** ❌ |

探针 [C] 拿到铁证（用真实的 `accounts.lastlogin`）：

```
原始显示值 (session tz 渲染) : 2026-09-20 08:48:47
UNIX_TIMESTAMP -> 真实瞬时   : ...000  (2026-09-20 00:48:47 UTC)
————————————————— GMT-8 下 —————————————————
应用 getTimestamp().getTime : ...000  (2026-09-20 16:48:47 UTC)   ★ 差 16.0 小时  ← 应用是对的，DB 是错的
————————————————— GMT+8 下 —————————————————
应用 getTimestamp().getTime : ...000  (2026-09-20 00:48:47 UTC)   ★ 差  0.0 小时  ← 应用会读错
```

⇒ **只改 config 不改 DB = 把"应用本来对"变成"应用读错 16 小时"。所以必须回填。**

## 二、⚠️ 最要紧的一个坑：登录态 30 秒判断

```java
// MapleClient.java:845  getLoginState()
if (rs.getTimestamp("lastlogin").getTime() + 30000 < Server.getInstance().getCurrentTime()) {
    state = LOGIN_NOTLOGGEDIN;                    // 判定"这次切频道已经过期"
    updateLoginState(MapleClient.LOGIN_NOTLOGGEDIN);
}
```

`updateLoginState(LOGIN_SERVER_TRANSITION)` 写的是**当前瞬时**，本来就是给这个 30 秒窗口用的
（`MapleClient:802-806`）。只改 config 不回填 ⇒ 读回来的旧值永远比真实早 16h ⇒
**这个条件恒为真 ⇒ 每次切频道/进游戏都被判为登录态过期**，玩家会被踢回登录界面。

**这就是"两件事必须一起做"的硬理由。**

## 五、一个**行为变化**（不是 bug，需知情）

`getTimeLeftForNextDay()`（`Server.java:470`）用默认时区算"下一个 0 点"：

- **现在**：GMT-8 的 0 点 = **北京 16:00** ⇒ 每日 BOSS 入场次数在北京时间下午 4 点重置
- **改后**：北京 0 点 ⇒ 重置变成**北京时间 00:00**

影响 `BossLogTask`（每日 BOSS 入场）与 `FamilyDailyResetTask`（家族每日重置，仅开家族系统时）。单机下"0 点重置"更符合直觉，算改善。

### 8.2 ⚠️ 更正 §二 的措辞：回填从「硬性必须」降为「推荐（更干净）」

对**改动之后**新写的值，写入与读出用的是同一个时区（探针 [B]：GMT+8 下 `setTimestamp` 发的是北京时间字面量），
一进一出相消 ⇒ **新数据天然自洽**。
所以 §二 那句"读回来的旧值永远比真实早 16h"只对**改动之前已写进 DB 的那一批值**成立，
**不影响之后每次切频道新写的那条**。

再加上 `Server.java:768` 启动时必跑 `UPDATE accounts SET loggedin = 0` ⇒ 重启后 `loggedin` 是 0，
`getLoginState()` 里那个 30 秒分支（`if (state == LOGIN_SERVER_TRANSITION)`）**根本进不去**。
⇒ **不回填也不会出现"切频道被踢"。**

**但结论仍然照原方案回填**：成本只有 1 条 UPDATE，换来"DB 里时间口径统一"，不留历史包袱。
（回填**必须在停服状态下做** —— 否则会把重启后新写的值也一起 +16h，§六 已注明。）

### 8.3 补两个之前没写的证据点

- **日志 16h 差的出处**：`FilePrinter.java:74-75` 用 `new SimpleDateFormat("yyyy-MM-dd")` + `Calendar.getInstance()`
  取**默认时区**来算 `logs\<日期>\` 目录名 ⇒ 连目录名都慢 16 小时。改完这一项立刻变北京时间。
- **全项目只有 2 处 SQL 侧时间比较，且都不跨域**（两边都在 MySQL 侧）⇒ 与 JVM 时区无关：
  `MapleCharacter:7473` `DATEDIFF(NOW(), when) < 30`、`MapleSessionCoordinator:568` `expiresat < CURRENT_TIMESTAMP`。
  ⇒ **不存在"应用写入的列被 SQL 拿去和 `NOW()` 比"这种真正的错位**（最接近的是 `MapleSessionCoordinator:568`，§四已列，改完反而被修好）。

### 8.4 顺带 bug 补一条

`MapleClient.java:661` 的 `blubb == 0`（`rs.getLong("tempban")`）同 §四 那条：`getLong` 读这列返回**年份 2018** ⇒
前半恒假，真正兜住的是字符串比较。正确写法是 `rs.getTimestamp(col).getTime()`。**与本轮无关，单独立项。**

### 8.5 执行顺序结论：**先做时区，再谈连接池；两次重启分开做**

| 维度 | 时区（本文档） | 连接池（`修复E-HikariCP连接池方案.md`） |

| 重编译/打包 | ❌ 不用 | ✅ 必须，且 `jar uf` **前必须先停服**（jar 被 JVM 占用） |
| 可逆性 | config 改回 + 反向 SQL | 回滚 jar |

- 顺带确认：**这台机器的 JVM 默认时区本来就是 `Asia/Shanghai`**，是服务端显式 setDefault 成 GMT-8 才造成 16h 错位（不是机器时区本身有问题）。
