## 一、速查表

| 想法 | 能不能做 | 说明 |
|---|---|---|
| **按 Z 键全屏捡** | ⚠️ 有条件 | 屏幕内**至少要有 1 件物品**，否则客户端根本不发包 |

## 二、为什么「身边没物品按 Z」做不到（这是客户端限制）

### 客户端做了什么
按「拾取物品」键时，**客户端自己**先在 **800×600 屏幕范围**内找最近的掉落物。
**一件都找不到就不发包**。服务端收不到包，自然无从下手。

所以你观察到的现象更准确的说法是：**屏幕里要有物品**（不是"必须贴身站在物品旁"）。
只要屏内有物品，哪怕离得很远，Z 键也已经能捡完整张图了。

### 为什么修不了
这个判断写在**客户端二进制**里，服务端改不了。服务端能做的只是"收到包之后怎么办"。

### 为什么表情键可以
表情键**没有前置判断**，按下去一定发 `FACE_EXPRESSION` 包。所以拿它当"信号键"最合适。

### 10 秒自己验证一次
`config.yaml` 里 `USE_DEBUG_SHOW_RCVD_PACKET: true` 已开着（`MapleServerHandler.java:190` 打印每个收到的包，
忽略 167/197/89/91/41/188/107 七个高频包）：

1. 看着服务端控制台
2. 按一下**好友键** → **没有任何新行** = 铁证（UI 键不发包）
3. 按一下 **Z**（身边有物品）→ `Received packet id 202`（`ITEM_PICKUP = 0xCA`）
4. 按一下 **F1** → 出现 `FACE_EXPRESSION` 对应的包 id，然后聊天框冒出「全屏捡取：已拾取 N 件物品」

### 关键限制：数据包里不带「是哪个键按的」
所以没法做「Z 正常捡 + 另一个键全屏捡」这种"同包不同响应"。要独立键，只能用
**会发包的载体**（表情 / 道具 / 技能）——见下面的附录。

## 三、已实施方案

### Java 层（3 个文件）

| 文件 | 作用 |
|---|---|
| `src/server/GmActions.java` | **新增**。共用实现：`pickUpWholeMap(chr)` 和 `vacuumMonsters(chr)` |
| `src/net/server/channel/handlers/ItemPickupHandler.java` | 按 Z（`ITEM_PICKUP`）→ 调 `GmActions.pickUpWholeMap`。**原版非 GM 逻辑原样保留** |
| `src/net/server/channel/handlers/FaceExpressionHandler.java` | 按 F1/F2 → 调共用实现；非 GM 与原版一致 |

抽 `GmActions` 的原因：同一件事有两个入口（按 Z / 按 F1），必须保证走完全相同的代码。

### 两个开关

| 常量 | 位置 | 默认 | 作用 |
|---|---|---|---|
| `GM_ONLY_BULK_PICKUP` | `ItemPickupHandler` | `true` | 改 `false` 则**所有角色**按 Z 都全屏捡 |
| `MAX_BULK_PICKUP` | `GmActions` | `200` | 一次按键最多捡 200 件，防打爆网络（分批捡，不会一次发爆，见 §十） |
| `BULK_PICKUP_BATCH` | `GmActions` | `20` | 每批捡 20 件（分批调度，防一次发太多背包包把客户端卡死） |
| `BULK_PICKUP_BATCH_DELAY` | `GmActions` | `300` | 每批间隔 300ms（毫秒） |

### 吸怪用的是哪个方法

`MapleMonster.resetMobPosition(Point)`（`MapleMonster.java:1325`）内部依次做：

```
aggroRemoveController() → setPosition(newPoint)
→ map.broadcastMessage(moveMonster(...))   // 把新位置广播给客户端
→ map.moveMonster(this, position)          // 更新服务端侧的位置索引
→ aggroUpdateController()                  // 重新锁定最近的玩家（也就是你）
```

⚠️ **这个方法全项目此前零调用方**，而且怪物位置的最终显示是**客户端驱动**的
（`MoveLifeHandler:171` 转发客户端上报的移动）。所以这个包发出去客户端会不会照做，
**只能进游戏实测**。如果客户端不跟随，退路见 `GM指令扩展清单.md` 第五章方案 B。

### 安全性（都已复核）

- **归属**：`pickupItem` → `MapleMapItem.canBePickedBy()`（`:131`）⇒ **不会抢别人的掉落**
- **刚落地保护**：`dropTime` 400ms 内跳过（原逻辑也有）
- **背包满 / 唯一物品已拥有 / 前置任务不满足** → 直接跳过，不会刷一屏「背包已满」
- **队伍分钱、任务道具、脚本道具、宠物链路** 全部沿用原逻辑
- **迭代安全**：`getItems()` 内部已经把 mapobjects 拷成新 list（`MapleMap.java:3093`），循环中删对象不会 CME
- 宠物自动捡（`PetLootHandler`）就是"服务端主动多捡"的现成先例

## 四、⚠️ 怎么让它真正生效

> **服务端加载的是「编译产物」，不是 src！只改 src 不编译/不打包 = 完全没生效。**
> ⚠️ 补一条 2026-09-21 实测：**加载哪份产物取决于启动方式** —— 见 §七.5。
> - 从 IDEA Run/Debug 启动 → 加载 `out\production\SERVER083\` 里的 `.class`（本次实测就是这个）
> - 从 `start-server.bat` 启动（`java -jar`）→ 加载 `out\artifacts\...\HeavenMS-zhoubw_083.jar`
> ⇒ 最稳的做法：**IDEA 重新编译 + 重新打包 jar 两件都做**。

```bash
# 用现成的构建助手（本机 bash PATH 不稳，统一走 python 驱动）
py D:\tmp\mxd_build.py full     # 扫 src -> 编译 -> jar uf -> 校验条目数
```

手工等价命令：

```bash
javac -g -encoding UTF-8 -nowarn -d <临时目录> -cp "D:\MXDtestServer\cores\*" @<sources.txt>
cd <临时目录> && jar uf "...\HeavenMS-zhoubw_083.jar" .
```

- **必须带 `-g`**：IDEA 的 artifact 带 `LocalVariableTable`（= `-g`）。不加 `-g` 会让 jar 里近 900 个条目全变，就无法判断"到底改了什么"
- 校验：解包逐条目对比，**只应出现真的改过的类**。本次实测 = 新增 `server/GmActions.class` + 改动 2 个 handler，无丢失、manifest 未变
- 回滚备份：`saves\HeavenMS-zhoubw_083.jar.bak-20260921b`

### B. 用道具当载体
1. 客户端「系统 → 键盘设定」把某个键绑到一个指定消耗品（无用的冷门道具 ID）

## 六、键位在哪改（如果要换键）

服务端只认"表情值"，**不关心是哪个物理键**。所以换键有两种做法：

1. **改服务端常量**（推荐）：改 `FaceExpressionHandler` 里的 `EMOTE_BULK_PICKUP` / `EMOTE_VACUUM`，
   例如改成 `6` / `7` 就变成 F6 / F7
2. **改客户端键位**：游戏里「系统 → 键盘设定」，把 F6/F7 之类绑成"表情 1 / 表情 2"

两者配合即可做到"任意键触发"。键位数据存在 DB `keymap(characterid, key, type, action)`，
登录时由 `MaplePacketCreator.getKeymap()`（`:3637`）下发；游戏内改键走
`RecvOpcode.CHANGE_KEYMAP = 0x87` → `KeymapChangeHandler`（只校验 + 存库，不执行任何东西）。

## 七、菜单能吸怪 ⇒ F2 能不能吸怪？（2026-09-21 复核）

**结论：两条路径核心逻辑等价，三道前置关卡全部验证通过。唯一剩余的未知量是"表情值映射"—— 有强推导证据，但仍属实测前推断。**

### 7.1 两条路径逐行对比

| | 菜单路径（**已实测生效 ✅**） | F2 按键路径（待测） |
|---|---|---|
| 入口 | `gm_menu.js:447 vacMobs()` | `FaceExpressionHandler.java:69` |
| 取角色 | `cm.getPlayer()` | `c.getPlayer()` |
| 取怪 | `chr.getMap().getAllMonsters()` | `chr.getMap().getAllMonsters()` |
| 取坐标 | `chr.getPosition()` | `chr.getPosition()` |
| **核心调用** | `mobs.get(i).resetMobPosition(pos)` | `mob.resetMobPosition(pos)` |

`gm_menu.js:460` 与 `GmActions.java:128` 调的是**同一个服务端原生方法**（`MapleMonster.java:1325`）。
菜单既然能成，说明"服务端改位置 → 广播 `moveMonster` 包 → 客户端跟随"这整条链路是通的 —— **这是 F2 能生效的最强保证**。

**两处细微差异（都不影响"能否生效"）**：

- Java 版跳过 `!mob.isAlive()` 的怪，脚本版不判活 ⇒ 地图只剩"已死不活"的怪时，Java 版回「本图没有活着的怪物」，脚本版会照样报成功。
- Java 版逐只 `catch(Exception)` 静默跳过，脚本版单独统计失败只数。

### 7.2 三道前置关卡（测试前已全部验证）

| 关卡 | 结果 | 证据 |
|---|---|---|
| 1. 处理器是否注册到**频道服** | ✅ | `PacketProcessor.java:157`，且位于 `:127 else` 的 `//CHANNEL HANDLERS` 块内（**不是**登录服块）；`RecvOpcode.FACE_EXPRESSION(0x33)` |
| 2. `chr.isGM()` 能否通过 | ✅ | `MapleCharacter.java:6320` ⇒ `gmLevel > 1`；DB `characters.gm = 6`；菜单脚本 `gm_menu.js:604` 也是 `isGM()` 关卡，菜单能开 ⇒ 必然通过 |
| 3. 运行中的 class 是否新代码 | ✅ | 服务端进程 08:04:32 启动；`FaceExpressionHandler.class`/`GmActions.class` 编译于 07:53:13 ⇒ **产物比源码新** |

### 7.3 ⚠️ 唯一的未知量：表情值映射

`FaceExpressionHandler` 假定 **F1 发出的 `emote` = 1、F2 = 2**。推导链：

服务端自己的默认键位表（`GameConstants.java:280-282`）：

```
DEFAULT_KEY    ...  59,  60,  61,  62,  63,  64,  65 ...   ← F1~F7 的键码
DEFAULT_TYPE   ...   6,   6,   6,   6,   6,   6,   6 ...   ← 6 = 表情
DEFAULT_ACTION ... 100, 101, 102, 103, 104, 105, 106 ...   ← 表情动作号
```

与 DB 实测**完全吻合**（`keymap` 表：59→100、60→101 … 65→106，`type` 全为 6）。
取 `emote = action − 99` ⇒ **F1→1、F2→2**，与代码常量一致。两套键位表（`DEFAULT_*` 与 `CUSTOM_*`）都是这个规律。

> 但客户端二进制里究竟发几号，**只能按下去看**。§7.4 就是为此准备的。

### 7.4 测试判定树

服务端已开 `USE_DEBUG_SHOW_RCVD_PACKET: true`（`config.yaml:213`），且 `51`（=0x33）**不在**忽略列表
（忽略的是 167/197/89/91/41/188/107）⇒ 每按一次 F2 必定打印一行 `Received packet id 51`。

| 现象 | 含义 | 处理 |

| 怪被拉到脚下 + 聊天框「[GM] 吸怪：已把 N 只怪拉到脚下」 | ✅ 全部正确 | 收工 |
| **人物做了表情**、无 GM 提示、控制台有 `Received packet id 51` | 包到了但 `emote ≠ 2` | 把 `EMOTE_VACUUM` 改成实际值 |
| 控制台**没有** `Received packet id 51` | 客户端压根没发包 | F 键在此客户端未绑表情 ⇒ 走备选方案（道具/技能载体，§五） |
| 按 F2 反而**捡了地上的东西** | `emote` 比预期小 1（F2 发的是 1） | `EMOTE_BULK_PICKUP` 改 2、`EMOTE_VACUUM` 改 3（整体 +1） |

### 8.1 第一轮结论作废

第一轮看到 `useslots=32/32`、`etcslots=32/32`，判断是 `checkSpace` 预检把东西全跳过。
第二轮用户按方案一扩了背包（USE 104 / ETC 112 / EQUIP 120，实际占用仍是 32/32/32），
**F1 依然一件不捡** ⇒ 空间不是原因。

同时查实：

- `logs\...\error\game\packethandler\` 下**没有** `FaceExpressionHandler.txt` ⇒ 处理器跑完了、**没抛异常**；
- `RecvOpcode.FACE_EXPRESSION(0x33)` 在 `PacketProcessor:157` 已注册；
- ⚠️ **第二轮测试其实跑的还是旧代码** —— 服务端（IDEA 启动）加载 `out\production\SERVER083`，
  而当时的构建脚本只更新 jar，**没往这个目录写**。详见 `handbook\GM自动隐身-怪物不动-根因.md` §五。

### 8.2 认知更正：GM 按 Z 走的也是这条代码

`ItemPickupHandler.java:58`：

```java
if (!GM_ONLY_BULK_PICKUP || chr.isGM()) {
    ... GmActions.pickUpWholeMap(chr) ...   // ← GM 按 Z = 全屏捡取，不是原版单件拾取
    return;
}
```

⇒ **GM 的 Z 键和 F1 是同一段代码**，所以"Z 键会弹「背包已满」"的说法作废（旧代码在 picked==0 时只发 `enableActions`）。
两者差别只在**客户端**：按 Z 时客户端先在 800×600 屏内找最近掉落物，一件都没有就**根本不发包**；F1 没有这个前置判断。

### 8.3 "人物不显示 / 怪物不动 / 按左右像瞬移 / 只能靠 `!h` 现身"

**两个并存的变量，第三轮才分清（详见 §九）**：

1. **F1 这个键本身**（**主因**）：客户端自己处理 F1，表现为隐藏人物 + 怪物停住 + 位移感。
   改绑到 X 后这一组现象**全部消失** ⇒ 这就是它。
2. **`config.yaml:224 USE_AUTOHIDE_GM`（GM 进游戏自动隐身）**：独立变量，属于服务端侧
   —— 隐身玩家永远当不了怪物控制器（`MapleMonster:1853 if (!chr.isHidden())`）⇒ 怪物不走；
   同时服务端给自己发 GM 隐身效果包 ⇒ 自己看不见自己。
   已改为 `false` 以消除干扰。完整证据链 → `handbook\GM自动隐身-怪物不动-根因.md`

**最简单的判定**：不按 F1、也不打 `!h`，直接登录看看人物是不是可见 ——
不可见 ⇒ 是第 2 条（自动隐身）；可见 ⇒ 是第 1 条（F1 键）。

### 8.4 已修 + 待验

**已修（需重启服务端生效）**

1. `picked` 改判 `mapitem.isPickedUp()`，不再虚报件数；
2. **400ms 落地保护的时钟统一** —— `dropTime` 来自 `Server.getCurrentTime()`（服务端集中时间），
   旧代码却拿 `System.currentTimeMillis()` 去比，两只时钟一有偏差就会把"刚掉落"全部跳过；
3. 失败原因**分项提示**（`PickupReport`：背包满 / 刚掉落 / 归属他人 / 任务限定 / 已捡走 / 被拒）；
4. F1/F2 执行后若处于隐身，会附加一句提示（`warnIfHidden`）。

## 九、★★★ 定案：GM 功能该绑哪个键（2026-09-21 实测）

### 9.1 决定性实验

| 绑的键 | 表情值 | 结果 |
|---|---|---|
| **F1** | 表情 1 | ❌ **毫无反应**（捡不到任何东西）。而且按 F1 后**人物消失、怪物静止不动**、按左右像瞬移，再按一次 F1 人物又出现，只能靠 `!h` 真正现身 |
| **X**（用户把「表情 1」改绑到 X） | 表情 1 | ✅ **全屏捡取立刻正常**（东西全捡起来），**且不再出现人物消失 / 怪物不动** |

**同一个表情值、同一段服务端代码，只换了物理按键，结果完全不同**
⇒ **F1 不是"服务器不认"，而是"客户端自己在处理 F1"**：

> 按 F1 时，北冥客户端执行了自己的某个 GM 相关功能（表现为隐藏人物 + 怪物停住 + 位移感），
> **根本没有发出 `FACE_EXPRESSION` 包** ⇒ 服务端收不到 ⇒ GM 快捷键毫无反应。
> 之前看到的"按 F1 人物隐身"其实全是**客户端 F1 自己的行为**，与服务端、与 `USE_AUTOHIDE_GM` 都不是同一件事。

### 9.2 结论 / 选键规则

1. **⛔ GM 功能键绝对不要用 F1**（该键已被客户端占用）。
2. **✅ 推荐用客户端没占用的普通键**：X（已实测）、C、V 之类。
3. ⚠️ 这里服务端绑定的是**「表情值」而不是物理按键** —— 按键由**客户端键位设置**决定：
   - 服务端认 `emote` 1 / 2 → 分别对应「表情 1 / 2」；
   - 你在客户端把「表情 1」绑到哪个键，哪个键就是"全屏捡取"。
4. 所以**换键完全不用改服务端代码、不用重编译**，只在客户端键位设置里改绑定即可。
   ⇒ 这也是本轮排查绕圈的根本原因：**改了半天服务端代码，而问题在客户端按键上**。

### 9.3 这张表建议的最终键位（09-21 实测收官）

| 客户端里绑定 | 服务端行为 | 实际使用 |
|---|---|---|
| 表情 1 | 全屏捡取 | **A**（✅ 用户实机确认可用；X 亦验证过 ✅） |
| 表情 2 | 吸怪 | **F2**（✅ 实测可用，继续沿用没问题）；想腾出 F 键可改 C / V |
| 表情 3 | （无功能） | **不必绑定** —— 原先的 GM 自检已撤（§9.6） |

⛔ 唯一禁区：**别把任何 GM 功能绑到 F1**。

### 9.4 一次测试就能定性：怎么区分"包没来"和"包来了被过滤"

**现在不用探针也能判**（见下表）；如果还想要更硬的证据，把 `GM_EMOTE_ECHO` 那两行临时加回去

`chr.dropMessage(6, "[GM] 收到表情值 emote=" + emote);`），它会把服务端**实际收到的 emote 值**回显出来。

| 现象 | 结论 |
|---|---|

| 弹出 `emote=N`，N 不是预期的 1/2 | 键位没绑对（绑到别的表情项上了） |

### 9.5 教训（下次别再绕）

- **报"按键没反应"时，第一步先确认包有没有到服务端**，别先怀疑业务逻辑 —— 这次绕了两轮，一轮是构建目录没写对（见 §8.1），一轮是按键被客户端吞了。

## 十、★★★ 全屏捡物卡掉游戏 → 分批异步修复（2026-09-22）

### 10.1 现象
地图物品一多，按全屏捡取（A = 表情 1）→ **画面卡死 + 被踢下线**。

### 10.2 根因（源码坐实）
旧 `pickUpWholeMap` 在**单个按键处理**里**同步循环**最多 200 件；每件走
`pickupItem` → `MapleInventoryManipulator.addFromDropInternal` 各发一个
`modifyInventory` 背包更新包（`MapleInventoryManipulator.java:212/235/251/263`）。

- 一次捡 200 件 ≈ 客户端瞬间收 **600+ 个包**（旧客户端单线程处理封包）→ 卡死 / 崩溃；
- 同步循环太久 → 服务端把玩家判定为卡死 → **踢下线**。

### 10.3 修复（方案 B：分批异步，已实施）
`GmActions.pickUpWholeMap` 改为 `void` 分批异步版：

| 改动 | 说明 |
|---|---|
| 调度 | `TimerManager.getInstance().register(task, BULK_PICKUP_BATCH_DELAY, BULK_PICKUP_BATCH_DELAY)` 周期任务，每批 20 件、间隔 300ms |
| 停止条件 | 换图 / 下线（`chr.getMapId()!=targetMapId \|\| !chr.isLoggedin() \|\| getClient()==null`）→ 自动停；本批没满（无可捡）→ 停；达 `MAX_BULK_PICKUP` 上限 → 停 |
| 挡重入 | `bulkPickupFutures.get(chr.getId())` 未完成则直接返回"进行中"，防连按叠加 |
| 统计 | `pickBatch(chr, rep, limit)` 同步捡一批（归属 / 400ms 落地保护 / 背包空间 / 任务限定沿用旧逻辑）返回本批进背包件数；`stop(msg)` 汇总发提示，`picked==0` 时发 `enableActions` 让客户端恢复 |

调用方改为只调 `GmActions.pickUpWholeMap(chr)`（不再读 `PickupReport`）：
- `FaceExpressionHandler.java`：去掉 `PickupReport rep = ...; chr.dropMessage(6, rep.toMessage());`
- `ItemPickupHandler.java`：同上（保留 `return;`，`enableActions` 已内置在 `stop` 里）

新增 import：`java.util.Map` / `ConcurrentHashMap` / `ScheduledFuture` / `tools.MaplePacketCreator`；
常量 `BULK_PICKUP_BATCH=20` / `BULK_PICKUP_BATCH_DELAY=300` / `bulkPickupFutures`（按角色 id 记进行中的 future）。

### 10.4 部署 + 验收
- 部署：`deploy_classes.py` + `patch_jar.py` 双更新成功（jar 条目 **2029 → 2030**，多出的 1 个 = 新增匿名类 `GmActions$1`，属正常新增，其余类就地更新无重复）。
- 生效：**重启服务端** + 完全关客户端重开。
- 验收：地图物品多时按 A → 看聊天框**分批进度提示**、不再卡死 / 被踢；换图自动停、再按提示"进行中"。
