> `calcDmgMax` 是 `(int) Math.ceil(double)`（`MapleCharacter.java:810`），Java 的 `double→int` 是**饱和转换**
> ⇒ 钉在 `Integer.MAX_VALUE`，**不会变负**。这是全链路唯一一处 Java 兜底。

## 5. ⚠️ 三个副作用（改前已知情，这里留档）

1. **魔攻对战士完全无用** —— 拳套（KNUCKLE）走物理公式，且 `localmagic` 在 `MapleCharacter.java:7821`
   被 `Math.min(…, 2000)` 卡死。229,369 的魔攻是**纯摆设**，不报错也不生效。
2. **面板四维 262,136 是从未验证过的量级** —— 客户端此前只实测到 42,766（基础 32767 + 帽子 9999）显示正常；
   26 万这一档**只能上机看**（服务端 int 侧无问题）。
3. **伤害可能撞上「总伤害 int 溢出」** —— `AbstractDealDamageHandler.java:261/288` 的
   `totDamageToOneMonster` 是 `int`、累加零保护 ⇒ **单段 × 段数 ≥ 2,147,483,647 会溢出变负**，
   `MapleMonster.java:365` 走 `delta<0` 分支 ⇒ **怪物回血、打不死**。段数多的技能尤其明显。

   风格不符就**中止**，不要"猜着补"，否则会插重复节点（见第 1 条）。
4. 写完**立即回读校验** + `xml.etree` 解析 + 无 BOM + CRLF 保持。
5. 最后一定跑**真 Java 探针**（服务端自己的读取器），Python 解析只能证明"文件没坏"，证明不了"服务端认"。
