## 一、需要你决定的问题

### 🔴 P1 · 固定圈心带来的新代价：围栏会「抖动」

**这是本次「固定圈心」改动**新引入**的行为**（原来圈心跟着人走，不会出现"人走了怪还留在原地"的持续越界）。

**机制**（围栏任务每 400ms 跑一轮，`MapleMap.startVacuumFence`）：

```
玩家站在圈心附近打怪
怪想攻击玩家 → 往玩家方向走 → 离圈心 > 100px → 被判越界
  → resetMobPosition() 拉回圈心
    → 含【map.broadcastMessage(moveMonster)】全区广播
    → 含【aggroRemoveController() + aggroUpdateController()】= 又一次全区广播（换控制器）
怪被拉回后又继续往玩家走 → 400ms 后再越界 → 再广播 ...
```

**关键**：`resetMobPosition`（`MapleMonster.java:1325`）**每次都广播两次全区包**。围栏一旦进入这个循环，就是 **每 400ms × 每只怪 = 2 个全区包**，且**永不停止**。

**加重场景**：玩家走远后（比如去捡东西），怪被钉在圈心、玩家不在附近 ——
**这些包完全没人需要**（附近没玩家），纯属白烧带宽；若附近恰好有别的玩家，他看到的是「一群怪在原地抽搐」。

**建议修法**（改动很小，只在围栏任务里加一个短路）：

```java
Point center = vacuumCenter;
if (center == null) { stopVacuumFence(); return; }

// [新增] 人离圈心太远 → 本轮什么都不做（既省包，也避免"抽搐"观感）
int dx = attractor.getPosition().x - center.x;
int dy = attractor.getPosition().y - center.y;
if ((long) dx * dx + (long) dy * dy > 800L * 800L) {
    return;   // 阈值可调，800px ≈ 40 身位
}
```

**要不要改由你定**：如果你就是「站在开通点不动」的打法，P1 几乎不会触发；如果你习惯边打边走，建议加上。

**✅ 处置（2026-09-24 傍晚，用户拍板）**：不采纳"人走远暂停"，改为**从根上换掉落点算法** —— 见 `好玩改动-跨图吸怪与全怪物点名.md` **§12.4「软围栏」**：

- 落点由「跳回圈心附近随机点」→ **沿「圈心 → 怪」的射线按回圆周**：位移 = 越界量（约 24~30px），方向顺着怪原前进方向；
- `VACUUM_FENCE_INTERVAL` 400 → **250** ms。

⇒ **"抽搐"观感基本消除**（不再出现上百 px 的大跳，改为"贴着看不见的墙滑"）。但**包量问题依旧**：怪贴墙时仍每 tick 走一次 `resetMobPosition`（= **3 个包**：1 个全区广播 `moveMonster` + 2 个单播 `stopControllingMonster` / `controlMonster`）。本段提到的两个优化（"人走远暂停"、"轻量回推不重打控制器"）**本次均未采纳**，列为可选后续项。

### 🔴 P2 · 开吸怪时召唤扎昆，手臂和三个形态都会被搬到圈心

**调用链已核实**（`MapleMap.java:1856`）：

```
脚本 map.spawnMonsterOnGroundBelow(m0, point)      // 9010000.js:1804 / 1818 / 1822
  → MapleMap.spawnMonsterOnGroundBelow(mob, pos)   // L1856
    → mob.setPosition(spos); spawnMonster(mob)     // L1860-1861
      → spawnMonster(monster, 1, false)            // L2096
        → attractIfEnabled(monster)   ← 这里！      // L2115
```

`attractIfEnabled`（L2081）**没有任何 BOSS 过滤**，只要 `autoAttract` 开着，**任何**经由 `spawnMonster` 出来的怪都会被搬到固定圈心附近（±100px 随机）。

**后果**：
1. **8 条手臂被叠到同一个圈里** → 同时放技能 → 正是「8 臂扎昆丢技能卡掉线」的成因之一
2. 三个形态（8800000/8800001/8800002）出现的位置被你**拉离**原定召唤点，「分段副本」的空间感没了
3. 如果你在**城镇图**开吸怪再召唤 BOSS，这一条会叠加之前的"视野半径"问题，卡得更快

**建议修法**（一行）：

```java
private void attractIfEnabled(MapleMonster m) {
    if (autoAttract && attractor != null && vacuumCenter != null && attractor.getMap() == this) {
        if (m.isBoss()) {          // [新增] BOSS 不进围栏
            return;
        }
        m.resetMobPosition(new Point(
                vacuumCenter.x + Randomizer.nextInt(VACUUM_WANDER_RADIUS * 2 + 1) - VACUUM_WANDER_RADIUS,
                vacuumCenter.y));
    }
}
```

`isBoss()` 是 `MapleMonster` 的现成方法（`MapleMonster.java:949` 已在用），无需新写。

> ⚠️ 注意：加了这行之后，「吸血怪打 BOSS」的玩法就没有了 —— 如果你**就是想**把 BOSS 吸过来打，那就**不要**加，但请把「开吸怪时别召唤扎昆」当成一条纪律。

### 🔴 P3 · `MonsterListener` 分发没有异常保护（本次只是打了补丁）

**本次修的是什么**：`MonsterListener` 接口有 3 个抽象方法（`MonsterListener.java:6-8`），脚本用 JS 对象实现它。之前脚本里只写了 `monsterKilled` / `monsterDamaged`，**漏了 `monsterHealed`** → 扎昆手臂回血时 → Nashorn 对未实现的方法抛 `UnsupportedOperationException` → **刷屏**。本次在 3 处 listener 都补上了 `monsterHealed`（`9010000.js:1829/1833/1837`）✓ **修得对**。

**但根因没解决**：分发器本身**没有任何容错**（`MapleMonster.java:928-930` 与 `942-944`）：

```java
for (MonsterListener listener : listenersList) {
    listener.monsterHealed(trueHeal);      // 抛异常 → 直接冒泡出去
}
```

也就是说：
- **任何一个** listener 在任何**一个**回调里抛异常，都会**中断这次击杀 / 受伤 / 回血的后续处理**（掉落、经验、公告等都在后面）
- 以后谁再写一个新的 JS listener 忘了补某个方法，**同一种事故会再来一次**
- `monsterKilled` / `monsterDamaged` 也有完全相同的隐患（本次没碰）

**建议修法**（治本，3 个分发器统一改）：

```java
for (MonsterListener listener : listenersList) {
    try {
        listener.monsterHealed(trueHeal);
    } catch (Throwable t) {
        // 单个 listener 出错不能影响框架本身
    }
}
```

**注意**：改的是 `MapleMonster.java`（不属于本次待提交改动），属于**新增改动**，要重新编译 + 重启。

### 🟡 P4 · `MobSkill` 的 debuff 优化：**改对了方向，但注释说反了，而且基本没效果**

**源码事实**（`MapleCharacter.java:2795`）：

```java
public void giveDebuff(final MapleDisease disease, MobSkill skill) {
    if (!hasDisease(disease) && getDiseasesSize() < 2) {     // ← 先判断
        ...
        client.announce(MaplePacketCreator.giveDebuff(debuff, skill));        // ← 才发包
        map.broadcastMessage(this, MaplePacketCreator.giveForeignDebuff(...));
    }
}
```

**结论**：
1. 「重复上同种疾病」**原本就不会发包**（判断在发包之前）。所以本次加的 `if (character.hasDisease(disease)) continue;` 注释里写的「拒绝发生在【包已经发出去之后】」是**与源码相反的错误描述**，应改成：「提前跳过，避免无谓的 `giveDebuff` 调用；真正省下的是 SEDUCE 的 10 人名额」。
2. 本次改动**唯一真实收益**：SEDUCE 分支的 `i < 10` 名额不再被「已中病的玩家」白白占用（原代码 `i++` 是无条件执行的）→ 实际能定身到 10 个**不同**玩家。**收益很小但真实**。
3. **没覆盖**的另一种情况：玩家已中 2 种其它疾病时（`getDiseasesSize() >= 2`），`giveDebuff` 仍会被调用一次（内部拒绝，不发包）→ 有极小的调用开销。

**处理建议（二选一）**：
- **A（推荐，最省事）**：保留代码，把注释改对 —— 它无害，且 SEDUCE 名额那条是真收益
- **B**：直接回退 `MobSkill.java`，因为这条改动与「减少了封包」的初衷不符

> 📌 这条不影响游戏行为，**今晚测不测都行**。

### 🟡 P7 · 脚本去掉了逐件 try/catch，异常时会「静默半途而废」

旧版：

```js
for (...) { try { MIM.removeFromSlot(...); total++; } catch (e) { failed++; } }
```

新版（`:2154-2158`）：

```js
var before = inv.list().size();
MIM.removeAllItems(client, invType, false);
var after = cm.getInventory(invType).list().size();
total += (before - after);
```

**风险**：`removeAllItems` 一旦抛异常（例如 `c.getPlayer()` 为 null、宠物处理异常），**整个 `doClearBag` 会中断**：
- 后面的栏位不再清理
- **不会有任何提示**，GM 会以为"清完了"
- 好消息：服务端侧有 `finally { inv.unlockInventory(); }`，**不会锁泄漏**

**建议**：脚本侧包一层，至少报个错：

```js
try {
    MIM.removeAllItems(client, invType, false);
} catch (e) {
    cm.dropMessage(5, "[GM] 清理 " + BAG_TYPES[i][1] + " 出错：" + e);
    continue;
}
```
