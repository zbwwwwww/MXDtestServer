# 装备属性上限与安全改法（四维 / 速度 / 跳跃）

> 2026-09-22 · 起因：用户问「维泽特帽的四维最高能改到多少？速度和跳跃最高能改到多少不会出 bug？」
>
> **一句话结论**：**四维硬顶 `32767`；速度最多给 `+40`、跳跃最多给 `+23`（客户端上限），再多**无效但不报错**；任何一项超过 `32767` 会静默变成负数（真 BUG）。**
>
> ⚠️ **2026-09-22 08:17 本文结论已落地**：维泽特帽 `incSTR/DEX/INT/LUK → 32767`（硬顶）、
> `incSpeed → 40`、`incJump → 35`，**wz 与手上那件的 DB 记录都改了**。执行记录见文末附录。

## 一、结论速查表

| 属性 | ① 硬性技术上限<br>（协议层，超了必坏） | ② 客户端"有效"上限<br>（超了纯浪费） | ③ 建议取值 | 超限后果 |
|---|---|---|---|---|
| `incSTR` / `incDEX` / `incINT` / `incLUK` | **32767** | 无（客户端按 `int` 叠加显示） | ≤ 32767<br>（保守 ≤ 30000） | ①②之间正常；>32767 **静默变负数** |
| `incSpeed` | **32767** | **+40**（总速度 140 封顶） | **40** | 40~32767：被丢弃，**无效但无害**<br>>32767：变负数 |
| `incJump` | **32767** | **+23**（总跳跃 123 封顶） | **23** | 23~32767：被丢弃，**无效但无害**<br>>32767：变负数 |

> ⚠️ ② 那一栏是**"全身装备 + BUFF 加起来"**的可用额度，不是单件。帽子一件给满 40/23 之后，
> 再穿鞋子(+5)/披风(+10)/开轻功(+20) 等，超出的部分照样被丢弃 —— 但也不会坏。

**维泽特帽现状（2026-09-22 08:17 起）**：四维 `32767`、`incSpeed = 40`、`incJump = 35`
- 四维：**32767 = `short` 硬顶，已到这一层的天花板**（见 §2）
- 速度：总 140，**正好顶满**客户端上限 ✅
- 跳跃：总 **135，超上限 12 点** ⇒ 那 12 点是白给的（装备侧有效上限只到 +23）。
  取 35 而非 23 属"数值冗余但无害"；想每分都生效就写 23
- （早期实测跳跃 50 "没问题" 正是这个原因：**不是没触发上限，是超出的部分本来就被丢弃**）

## 二、为什么是 32767 —— 源码证据链

### 2.1 硬墙：wz 加载走的是**裸 `(short)` 强转，没有任何保护**

`server\MapleItemInformationProvider.java` 加载装备模板时（`:1041~1064`）：

```java
if (stat.getKey().equals("STR"))        nEquip.setStr((short)   stat.getValue().intValue());
else if (stat.getKey().equals("DEX"))   nEquip.setDex((short)   stat.getValue().intValue());
else if (stat.getKey().equals("INT"))   nEquip.setInt((short)   stat.getValue().intValue());
else if (stat.getKey().equals("LUK"))   nEquip.setLuk((short)   stat.getValue().intValue());
...
else if (stat.getKey().equals("Speed")) nEquip.setSpeed((short) stat.getValue().intValue());
else if (stat.getKey().equals("Jump"))  nEquip.setJump((short)  stat.getValue().intValue());
```

`Equip` 里这些字段全是 `short`（`Equip.java:203/207/211/215/255/259`）。
**没有 `Math.min`、没有 clamp、没有报错** —— 写多少就 `(short)` 截多少。

### 2.2 对照：卷轴路径**有**保护 —— 说明开发者知道这个坑，只是没管 wz 加载

```java
// MapleItemInformationProvider.java:605~611
private static short getMaximumShortMaxIfOverflow(int value1, int value2) {
    return (short) Math.min(Short.MAX_VALUE, Math.max(value1, value2));
}
private static short getShortMaxIfOverflow(int value) {
    return (short) Math.min(Short.MAX_VALUE, value);
}
```

卷轴强化（`:623~639`、`:795~823`）全部走这两个函数 → **会被 clamp 到 32767**。
⇒ **同一个 32767 上限，卷轴撞上去会被挡住，wz 撞上去会直接翻负数。**

### 2.3 精确的溢出边界（用 JDK8 `jjs` 跑真实 Java 语义实测）

| wz 里写 | `Equip` 实际存 | 后果 |
|---:|---:|---|
| 9999 | 9999 | ✅ 正常（07:47 那版，已实测通过） |
| 30000 | 30000 | ✅ 正常 |
| **32767** | **32767** | ✅ **正常（上限，★ 当前值）** |
| 32768 | **-32768** | ❌ 属性反向 |
| 40000 | **-25536** | ❌ 属性反向 |
| 65535 | **-1** | ❌ 属性反向 |
| 65536 | **0** | ❌ 属性凭空消失 |
| 99999 | **-31073** | ❌ 属性反向 |

验证脚本：`D:\tmp\cap_limit_check.js`（jjs 跑，可复跑）

### 2.4 累加侧不会溢出（所以 32767 是唯一那堵墙）

| 环节 | 位置 | 类型 | 结论 |
|---|---|---|---|
| 装备字段 | `Equip.java:203~259` | `short` | ← **墙在这** |
| 装备属性封包 | `MaplePacketCreator.java:439~453` | `writeShort` | 同墙 |
| 人物装备累加 | `MapleCharacter.java:204~205` | **`int`** | ✅ 不溢出 |
| `getTotalStr/Dex/Int/Luk` | `MapleCharacter.java:5350~5364` | **`int`** | ✅ |
| 伤害计算 | `MapleCharacter.java:826` | `double` → `int` | ✅ |
| DB 列 | `characters.str` 等 | `int(11)` | ✅ 存储层很宽 |

⇒ **唯一的 16 位关口就是"装备自身"这一层。** 单件写到 32767 是安全天花板。

## 三、速度 / 跳跃：服务端**完全不限制**，瓶颈全在客户端

### 3.1 服务端侧：不存、不算、不校验

- `MapleCharacter` 里**根本没有 speed / jump 字段**（全源码 grep 确认）—— 服务端从不记录玩家当前移动速度。
- 人物属性封包 `MaplePacketCreator` **不发送** speed/jump（只有装备信息里带）。
- 移动处理 `MovePlayerHandler.java:29~46` 只做三件事：跳过 9 字节 → `updatePosition` 解析 → **原样广播**。
  **没有任何基于速度的校验、没有反作弊、没有踢人逻辑。**

⇒ **改高速度/跳跃，服务端不会把你踢下线。** 风险 100% 在客户端侧。

### 3.2 客户端侧：速度 140 / 跳跃 123 封顶（硬编码，改不了）

- 人物移动基线固定 **速度 100 / 跳跃 100**；装备上的 `incSpeed`/`incJump` 是**百分比叠加**在上面。
- **速度上限 140、跳跃上限 123**，超出部分**直接丢弃**（多个来源一致）：
  - 同类 083 私服的 `config.ini` 里就明写着 `speedMovementCap=140` / `jumpCap=123`
  - 客户端行为说明：「Both stats are capped, so stacking movement gear past the cap does nothing.」
- **本机北冥客户端没有这个配置文件** —— 已在客户端目录（含三层子目录）全盘搜过
  `.ini/.conf/.config/.cfg/.properties/*config*`：**命中 0 个**。
  ⇒ 说明这两个上限是**编译进 `Maplestory.exe`** 的，**无法通过改配置放宽**。

⇒ 装备侧的有效额度：**速度最多 +40、跳跃最多 +23**。

### 3.3 速度顶满了，跳跃还多给了 12 点

```
原版：总跳跃 = 100(基线) + 50(帽子) = 150   →  客户端取 123，丢掉 27 点
      总速度 = 100(基线) + 30(帽子) = 130   →  没到 140，10 点额度没用上

现在：总速度 = 100(基线) + 40(帽子) = 140   →  正好顶满 ✅ 每一分都生效
      总跳跃 = 100(基线) + 35(帽子) = 135   →  客户端取 123，仍丢掉 12 点
```

**如果你想让跳跃也"每一分都生效"**：帽子写 `incJump = 23` 就是最优解（现在写的是 35）。
（不过写多了也不会坏 —— 只是无效。**超过 32767 才会坏**，见 §二。）

## 四、四维还能加吗？—— 能，但先看客户端那一关

四维和速度/跳跃不一样：**客户端要显示"基础 + 装备"的总值**，而基础值已经顶满。

| 项 | 位置 | 值 |
|---|---|---|
| 基础四维（`characters.str` 等，**实测**） | 数据库 | **32767** ×4 |
| 帽子贡献（`inventoryequipment.str`，**实测**） | 数据库 | **32767** ×4 |
| 客户端实际显示的总值 | 客户端 | **65534** |

- 人物自身属性封包发的是**基础值**：`MaplePacketCreator.java:193 writeShort(chr.getStr())` —— 32767 在 `short` 范围内 ✅
- 装备属性封包发的是装备自身值：`writeShort(equip.getStr())` —— 32767 ✅
- **两个数在客户端相加** —— 42766 已超 `short` **有符号**范围，而你实测「没问题」
  ⇒ **客户端是按 `int` 处理总值的，没有 16 位有符号截断。** 这是最有力的实测证据。
- 当前总值 **65534 = 2¹⁶−2** —— 即便客户端按**无符号 16 位**存也刚好装得下，属最坏情况下的安全边界。
- 帽子改到 32768 时**装备层先翻负数**，根本到不了客户端。

⇒ **四维的安全上限：帽子 ≤ 32767。** 现已取到上限值 **32767**（服务端读取器实测无溢出，见文末附录）。

## 七、三条硬性提醒

1. **单值永远不要超过 32767** —— 这是唯一的"真 BUG 线"，越过去是**静默**的（没有报错、没有日志），只会看到属性莫名变成负数。
2. **速度（40）是三者里唯一没实测过的** —— 跳跃已被"50 无异常"间接验证（clamp 生效），
   四维已被"9999 无异常"验证（不按 16 位有符号截断）。速度的 140 上限是查证来的，**上机时留意走路/转向有无异常**。
3. **改 wz 必须重启服务端**（`equipStatsCache` 是内存缓存、无热重载）；改 DB 必须**先退游戏**（退出时 `saveCharToDB` 会把内存值写回，在线改会被覆盖）。
